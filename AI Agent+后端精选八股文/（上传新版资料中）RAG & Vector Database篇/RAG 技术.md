### 1. 请说明 RAG 的基本原理，并对比 RAG、微调、长上下文三种方案在知识更新、成本、可解释性和效果上的差异。

先讲原理：RAG 到底在解决什么问题。 大模型的知识固化在参数里，训练截止之后的事情它不知道，企业私有文档它也没见过。微调可以把新知识“写进”参数，但代价高、更新慢。RAG 换了一个思路：不改模型，而是在每次回答前，先从外部知识库把相关材料找出来，和问题一起交给模型，让模型“看着材料答题”。所以 RAG 本质是把“记忆”从模型参数里外置到可检索的知识库，模型负责理解和组织，知识库负责存储和更新。

RAG 的三个核心组件是：知识库（文档经过解析、切分、向量化后存入索引）、检索器（根据问题召回相关片段）、生成器（基于召回片段作答）。理解这三者的分工很重要——检索负责“找对材料”，生成负责“用好材料”，两者的失败模式不同，优化手段也不同。

再讲三种方案的对比逻辑。 对比不能只列结论，要理解每种方案为什么在某个维度上有优势或劣势：

- 知识更新：RAG 的优势来自“知识与模型解耦”——更新知识只需要更新索引，不动模型。微调的知识在参数里，更新要重新训练。长上下文是“临时塞入”，每次会话都要重新传，不沉淀。这里的关键判断是：你的知识更新频率有多高？ 高频更新场景下，RAG 是结构性优势，不是调优能弥补的。
- 成本：RAG 的成本结构是“检索服务 + 按查询计费的推理”，没有训练成本，且只把筛选后的证据送入模型，Token 消耗可控。微调有训练成本（GPU 时间）和持续维护成本。长上下文的成本最高——每次调用都为全部上下文付费，注意力计算随长度增长，长文档场景下延迟和费用都显著上升。这里的关键判断是：你是一次性投入还是持续性投入？ 微调是前期重投入，RAG 是随用量线性增长。
- 可解释性：RAG 能追溯到具体证据片段，这是它最容易被低估的优势。在合规、审计、客服等场景，“答案从哪来”和“答案对不对”同样重要。微调的输出无法追溯到训练样本，长上下文虽然材料都在，但模型答对时很难精确归因到某一段。
- 效果：这里要避免“RAG 一定更好”的误区。RAG 擅长事实型问答和幻觉控制，但不擅长跨多个不连续文档的复杂推理——检索器的局部召回可能漏掉推理链需要的某一块。长上下文在“需要全局视野”的任务上更强（跨章节总结、整本书分析），但存在“大海捞针”式的注意力丢失。微调擅长学格式、风格、领域语言模式，不适合承载大量事实知识，容易在未见事实上幻觉。

给一个判断框架，而不是死记结论。 面试时如果只背“RAG 更新快、微调成本高”，深度不够。更好的答法是给出决策逻辑：知识频繁更新 + 需要引用溯源 + 成本敏感 → RAG 为主；需要稳定的输出格式或领域风格 → 微调为辅；需要跨文档全局推理且文档长度可控 → 长上下文作为补充路径。三者不互斥，生产架构常见的是 RAG 承担事实检索、微调负责格式风格、长上下文在高价值查询上启用。

常见误区：把 RAG 当成“万能知识注入方案”，忽略检索失败会导致答案不完整；或者把长上下文当成 RAG 的替代品，忽略权限隔离和成本问题。面试时能指出这些边界，比罗列优点更有说服力。

### 2. 设计一个支持多文档格式、多租户、增量更新的 RAG 系统架构，并说明各模块的职责与关键接口。

先讲架构设计的思考起点：三个需求分别带来什么约束。 多文档格式要求摄入层能按格式路由解析器，并统一成可切分的中间表示；多租户要求隔离贯穿存储、检索、缓存三层，不能只在某一层做；增量更新要求写入路径支持“新版本写入 → 激活 → 旧版本清理”的完整生命周期，而不是简单覆盖。理解这三个约束，才能理解为什么架构要分层。

分层设计：每层解决一类问题。

- 摄入层解决“文档怎么进来、怎么变成可检索单元”。职责是按文件类型路由解析器（PDF 走布局感知解析、Word 按样式解析、HTML/Markdown 按结构解析、扫描件走 OCR），切分策略按文档结构选择，向量化异步批量执行。关键接口是 ingest(tenant_id, document, metadata) → job_id。这里的设计要点是异步化——解析和向量化是重操作，不能阻塞请求路径；以及版本化——新文档写入时带 version，为增量更新做准备。
- 索引层解决“检索单元怎么存、怎么更新”。职责是维护向量索引和元数据索引。关键接口是 upsert、delete、activate。增量更新的核心纪律在这里：先写新版本、再切换活跃指针、最后异步清理旧版本。如果直接覆盖，写入过程中查询会看到半新半旧的状态。多租户隔离策略也需要在这里决策：小租户共享索引 + 强制元数据过滤是内存效率最高的方式，大租户（超过十万级向量）应使用独立索引，避免跨租户召回干扰。
- 检索层解决“怎么找对材料”。职责是多路召回（向量 + BM25）、融合、重排。关键接口是 retrieve(tenant_id, query, filters, top_k) → evidence_list。两个设计要点：权限过滤必须在这一层完成，且过滤条件由服务端注入、不允许客户端覆盖；缓存 key 必须包含租户 ID 和知识库版本指纹，防止越权命中或命中已删除文档。
- 生成层解决“怎么用好材料”。职责是证据组装、提示词构建、受约束生成和引用校验。关键接口是 generate(query, evidence_list, tenant_config) → answer_with_citations。设计要点是每个证据带 evidence_id，生成后校验引用是否真实存在。
- 治理层解决“谁有权、出了事怎么查”。职责是权限管理、审计、监控和评估。关键接口是 authorize 和 audit。治理层不直接参与请求路径，但为检索层提供权限数据源，为监控提供 trace 字段。

多租户隔离要讲清楚“隔离点在哪”。 三个关键隔离点：摄入时按 tenant_id 分区存储原始文档和向量；检索时在索引查询中强制注入 tenant_id 过滤；缓存和引用记录按租户命名空间隔离。只做存储隔离不做检索过滤，等于没隔离——检索时仍可能召回其他租户的向量。

增量更新的设计要点是生命周期管理，不是单点操作。 更新不是“覆盖旧向量”，而是“新版本写入、激活、旧版本退役”的三步流程。删除也不是“删向量就完事”，而是要同步处理缓存失效和引用记录标记。这部分在面试中能展开讲，会显得对生产问题有实际理解。

### 3. 文档解析阶段如何处理 PDF、Word、HTML、Markdown、扫描件和表格？解析质量如何量化评估？

先讲一个核心原则：解析的目标是保留结构，而不是只抽取文字。 很多人把解析理解成“把文件变成字符串”，这是 RAG 质量问题的常见根源。一份双栏 PDF 如果只做文字抽取，左右栏文字会交错；一个表格如果变成文本行，行列关系就丢了；页眉页脚如果不删除，会污染每一个切分块。所以解析的第一原则是保留版面结构和阅读顺序。

分格式讲处理策略，重点讲“为什么”：

- PDF：最复杂，必须做版面分析。要先识别标题、正文、表格、图片、页眉页脚、脚注等区域，再重建阅读顺序（双栏必须左栏读完再读右栏），最后才抽取文本或 OCR。为什么要这个顺序？因为跳过版面分析直接 OCR，等于把结构信息扔掉了，后续切分再想恢复结构就来不及了。复杂 PDF 可选用 MinerU、Docling 等布局感知解析器。
- Word：自带样式信息（标题层级、列表、表格），优先按样式解析，成本低、结构准。不要回退到纯文本抽取，那会丢掉最宝贵的结构信号。
- HTML：利用 DOM 结构提取正文和标题层级，同时去除导航、广告、页脚等噪声。HTML 的挑战不是抽取，而是判断哪些是正文。
- Markdown：结构最清晰，直接按标题层级解析。一个实用做法是把所有格式统一转成 Markdown 再切分，这样跨格式的切分一致性更好。
- 扫描件：走 OCR 或 VLM 管线，输出必须带质量标注。为什么要标注？因为低质量 OCR 的文本进入索引后，检索可能命中但内容不可靠，生成阶段会把它当证据用。质量标注让下游能降权或排除。
- 表格：不能当普通文本。要保留表头与数据行的对应关系，转成 Markdown/HTML 或结构化 JSON 再索引。宽表按列拆或按行分组，避免单块过大。

解析质量怎么量化，要分两个层次讲。 文本层面用 NED（归一化编辑距离） 衡量抽取文本与人工参考文本的接近程度；表格层面用 TEDS（基于树编辑距离的表格相似度） 衡量表格结构还原的准确度。为什么需要两个指标？因为纯文本指标无法反映表格结构是否正确——一段文字可能字都对，但行列关系全错。此外，生产上还要监控解析兜底触发率（解析失败或降级到 OCR 的文档占比），这是运维指标，反映解析管线与文档分布是否匹配。

教学要点：面试时如果能指出“解析质量是 RAG 性能的主导因素之一”，并解释为什么（解析错→切分错→检索错→生成错，错误会沿链路放大），会比只罗列工具名更有深度。

### 4. 文本切分有哪些常见策略？如何根据文档结构、问题类型和 embedding 模型上下文长度选择切分方案？

先讲切分为什么重要。 切分是 RAG 链路的“中间环节”，但它的影响是放大的：切大了，检索精度下降（一个块混多个主题，向量变成平均值）；切小了，上下文不完整（答案被腰斩，模型拿到的证据缺条件、缺例外）。所以切分不是“随便切切”，而是在检索精度和上下文完整性之间找平衡。

常见策略及适用逻辑：

- 固定长度 + 滑动窗口：按 Token 数切，相邻块重叠 10%–20%。优点是简单、通用、可控；缺点是可能割裂句子和段落。适合作为默认基线，尤其文档结构不清晰时。
- 句子/段落级切分：按自然语言边界切，保语义完整。适合 FAQ、条款、日志等句子边界清晰的内容。
- 递归切分：段落 → 句子 → 词逐级回退，尽量在高层边界切，切不动再降级。适合非结构化散文和混合格式文档，是生产通用基线之一。
- 语义切分：计算相邻句子的 Embedding 相似度，在相似度骤降处切边界。适合语义连贯但结构不明显的长文本。代价是计算成本高、块大小不稳定。
- 结构感知切分：按 Markdown/HTML 标题层级切。适合格式规范的文档，性价比最高——结构本身就是语义边界。
- 父子分块：小块检索、大块生成。适合“检索要细、生成要全”的场景，是生产推荐方案。

选择切分方案要同时考虑三个变量，这是回答的深度所在：

文档结构决定“能不能利用结构”。 有清晰标题层级时，结构感知切分是首选，因为它是零成本的语义边界。结构混乱时，才退回到递归或固定长度。
