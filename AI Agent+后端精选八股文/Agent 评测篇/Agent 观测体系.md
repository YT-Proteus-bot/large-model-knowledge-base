### 01｜Agent 可观测性的核心指标应该怎么分层？任务级、模型级、工具级、成本级分别关注什么？

**核心判断：**分层的依据不是“数据来源”，而是“回答问题的粒度”。 任务级回答“这次任务整体怎么样”，模型级回答“推理花了多少、快不快”，工具级回答“外部调用稳不稳”，成本级回答“钱花在哪个环节”。四层必须能通过同一套 ID 关联起来，否则分层只是四张互不相干的报表。

- **任务级和模型级之间还有一个容易被忽略的中间层：**步骤级（**step span**）。 它承载 step_seq、当前意图、被判定的结果，是连接“任务总览”和“具体模型/工具调用”的桥梁。没有步骤级，定位失败时只能从任务直接跳到工具调用，丢失“**这一步在做什么决策**”的上下文。
- **一个关键的设计原则是“同一任务一条 Trace”。** 任务级指标和模型/工具级指标必须通过 trace_id 和 task_id 串起来，否则“这个任务为什么贵”和“这个模型调用属于哪个任务”无法回答。行业里一次简单 RAG 交互产生 3–10 个 LLM span，复杂多 Agent 会话可能是成百上千个，没有统一 Trace 就无法聚合。

**面试表达要点：任务级看整体结果和代价，模型级看推理效率和 token，工具级看外部稳定性和副作用，成本级看钱花在哪。中间要有步骤级做桥接。四层通过同一套 ID 关联，否则只是四张孤立的报表。**

### 02｜Agent 上线后，你通过哪些核心指标判断它表现好不好？成功率、延迟、成本之外还看什么？

**核心判断：**成功率、延迟、成本是必要但不充分的三个指标，因为它们只描述“**任务是否按预期结束**”，不描述“结束得对不对、稳不稳、可不可维护”。 Agent 的典型故障恰恰是：任务跑完了，没有报错，耗时和 token 都在正常区间，但结果是错的。“请求成功”不等于“任务成功”。所以判断表现好不好，必须补上三类指标：质量类、稳定性类、可维护性类。

1. **第一类：质量类（结果对不对） 。**业务验证通过率（不是“跑完”，而是输出被下游校验或人工确认）、关键约束遵守率、幻觉/事实错误率、引用忠实度、证据完整度。这一类指标回答“任务表面完成时，结果是否真的可用”。
1. **第二类：稳定性类（每次是否一致） 。**同一任务多次运行的输出方差、重试率、回退率、人工接管率、失败率按步骤的分布。重试率突然上升，往往不是模型的问题，而是某个工具开始变慢或开始返回格式错的东西。失败率按步骤分布能告诉你失败集中在规划、执行还是验证阶段。
1. **第三类：可维护性类（能不能持续变好） 。****平均定位时长（MTTD）、平均修复时长（MTTR）**、重复故障率、Trace 完整度、审计覆盖率。这四个指标持续下降，说明系统正在“可维护化”。一个当前成功率很高但 MTTD 很长的系统，下一次故障的代价会远高于一个成功率略低但定位很快的系统。

**还有一个常被漏掉的维度：**成本的结构而不只是总量。 **总成本低不代表健康**——可能是任务被大量跳过或降级；总成本高也不一定坏，可能是任务复杂度上升。应该看“一次成功任务的成本”（**cost per success**），以及模型、工具、人工等待各占多少。模型耗时占比、Tool/MCP 耗时占比、人工等待、测试与沙箱耗时应该被拆开看，而不是合并成一个“总耗时”。

**面试表达要点：**成功率、延迟、成本回答“跑没跑完”；质量类回答“跑得对不对”，稳定性类回答“每次是不是一样”，可维护性类回答“下次能不能更快修好”。只看前三项，会把“任务完成但结果错误”这种 Agent 最典型的失败漏掉。

### 03｜质量类指标能不能直接做告警？阈值应该基于什么来定，而不是拍一个单点数字？

**核心判断：**质量类指标可以做告警，但不能用“单点阈值 + 瞬时触发”的方式做。 质量指标天然有波动——模型输出有随机性，任务分布会漂移，样本量小时一个偶发错误就能让成功率从 98% 掉到 90%。直接拍一个固定阈值，结果要么误报太多导致告警疲劳，要么阈值太松导致漏掉真正的退化。阈值必须基于基线分布、样本量和误报/漏报的成本不对称来定。

第一，阈值应该来自历史基线分布，而不是一个绝对数字。 用过去稳定期的同任务类型数据建立分布，告警线设在分布的分位数上（比如 P5 或 P10），而不是“成功率低于 95% 就告警”。分布会随任务组合变化，所以基线本身需要按任务类型分群，而不是全局一个数。

第二，必须考虑样本量。 小样本下的质量波动很大，用固定阈值会频繁误报。告警应该基于滑动窗口内的样本量和置信区间，样本不足时降级为观察而不是告警。ReliAgent 在八个检测器中的七个上达到 0% 误报率，靠的不是固定阈值，而是对每个检测器单独校准的判定逻辑。

第三，误报和漏报的成本从来不对称。 为了压漏报把阈值调得很低，复核队列会爆掉，真正危险的告警反而沉在里面。所以阈值应该按业务后果分层：安全类、越权类、数据泄露类事件设零容忍门禁，不参与统计阈值；质量类用统计阈值，并接受一定误报，但要把告警送进有优先级的队列，而不是和所有告警混在一起。

第四，告警的对象应该是“变化”而不是“绝对值”。 质量指标从 97% 掉到 94% 可能比长期稳定在 93% 更值得关注，因为它说明系统在退化。CI/CD 质量门禁通过率及其随时间的变化趋势，比单次通过率更有诊断价值。

面试表达要点：质量指标可以做告警，但阈值要来自分任务类型的历史分布和样本量校准，安全类走零容忍门禁，质量类接受一定误报但要做告警分级。告警“退化趋势”比告警“绝对值”更有用。

### 04｜如何评估观测体系本身是否有效？误报率、漏报率、审计覆盖率这些指标怎么用？

核心判断：观测体系的有效性不是“有没有数据”，而是“出问题时能不能在可接受的时间内定位到根因，并且没有漏掉真正该发现的问题”。 误报率、漏报率、审计覆盖率分别回答“信不信得过”“有没有盲区”“覆盖够不够”，三者必须一起看，单独看任何一个都会得出错误结论。

误报率和漏报率应该成对使用，而不是单独优化。 只压低误报率，漏报会上升；只压低漏报率，告警队列会被淹没。有效的观测体系应该能报告每个检测器的混淆矩阵——TP、FP、FN、TN——而不是只报一个“准确率”。质量门禁的失败线可以用目标阈值的 70% 来区分“系统性故障”和“边缘不达标”：低于 70% 说明子系统根本坏了，介于 70% 和阈值之间说明需要人工分诊，不一定要触发硬告警。

审计覆盖率和 Trace 完整度是“盲区指标”。 可观测性的首要失败模式是遥测覆盖缺口（observability blind spots），即某个架构层根本没有数据。推荐的指标包括：全层 Trace 完整度百分比、每层评估覆盖率、生产事故的平均故障归因时间（MTTFA）。Trace 完整度应该按任务类型看，而不是全局一个数——一个整体 95% 完整的体系，可能在最复杂的多 Agent 任务上是 60%。

还有一个更根本的指标：观测体系能不能还原一次失败。 最小可观测对象应该覆盖任务层、步骤层、工具层三层。如果一次失败发生后，你不能按 task_id 找到任务总览、再下钻到失败步骤、再下钻到具体工具调用并确认根因分类（模型/工具/编排/数据），那么无论你的误报率多低，这个观测体系都是无效的。

面试表达要点：观测体系的有效性看三件事：误报和漏报的混淆矩阵而不是单一准确率、Trace 完整度和审计覆盖率有没有盲区、失败发生后能不能在 MTTD 内从任务下钻到根因。只看告警数量，等于没有评估观测体系。

### 05｜Agent 执行过程如何追踪？Task、Trace、Span、Event 分别应该表达什么？

核心判断：这四个概念不是同义词，它们分别表达“业务边界、链路边界、执行单元、时间点状态变化”。 混淆它们会导致两种错误：要么把 Task 和 Trace 当成一对一，丢失重试和续跑的关联；要么把 Event 和 Span 混在一起，让高基数的事件数据污染指标的标签空间。

Task 是业务维度的任务标识，绑定具体操作语义（比如 pay_20240517_8892），回答“这次业务任务是什么、最终状态是什么”。一个 Task 可能对应多次执行尝试，所以 Task 和 Trace 不是一对一。

Trace 是全链路唯一标识，贯穿调用栈，保障跨服务上下文可追溯。一次任务 = 一条 Trace 是常见的建模方式，但严格来说，Trace 表达的是“一次执行链路”，重试会产生新的 Trace，通过 parent_id 或 task_id 与原始任务关联。

Span 是执行单元，按角色分四类：task span（整个任务）、step span（一步决策）、model span（一次模型调用）、tool span（一次工具调用）。Span 有明确的开始和结束，承载操作名、耗时、状态和属性。

Event 是时间点上的状态变化，不是有持续时间的执行单元。关键事件时间线（task.started、memory.hit、retrieval.completed、policy.decision_made、approval.responded、task.ended）本身就是 Event 的典型用法。Event 适合记录“在 T+20s 策略决定暂停”“在 T+28s 人工批准”这类离散事实，而不是“一次调用花了多久”。

一个实用的区分规则：如果它回答“花了多久、做了什么操作”，它是 Span；如果它回答“在某个时刻发生了什么状态变化”，它是 Event；如果它回答“这次业务任务是什么”，它是 Task；如果它回答“这次执行链路怎么串起来”，它是 Trace。高基数的内容（如具体 prompt、工具参数）应该以关联 trace_id/span_id 的日志或事件承载，而不是直接塞进 Span 属性或指标标签。

面试表达要点：Task 是业务任务，Trace 是执行链路，Span 是有持续时间的执行单元，Event 是时间点上的状态变化。Task 和 Trace 可以是一对多（重试产生新 Trace），Event 不要和 Span 混用，高基数内容不要进指标标签。
