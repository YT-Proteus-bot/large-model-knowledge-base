### 1. 四者嵌套关系：租户是硬边界，用户是记忆所有权单位，Agent 和会话是检索投影

推荐的结构是租户强制隔离，其余三维作为同一租户内的作用域维度，而不是平级的四层嵌套：

```
代码块
tenant_id          ← 硬边界，存储层强制（RLS / 独立 shard / 独立实例）
  └─ user_id       ← 记忆所有权单位：一段记忆归属于谁
       ├─ agent_id ← 某个 Agent 写入/使用的记忆（可为空，表示用户级共享）
       └─ thread_id ← 会话级上下文，短期、易失
```

Oracle 的多租户 Agent 记忆 schema 就是按这个顺序设计的：每张持久化记忆表都携带 tenant_id, user_id, agent_id, thread_id 四个作用域列，但只有 tenant_id 由数据库行级安全（RLS）强制，其余三个是应用层提供的过滤条件。理由是：租户之间的泄露是“不可接受”级别的，必须结构性阻断；用户、Agent、会话之间的边界则需要在产品语义上灵活调整（比如团队共享、Agent 间协作），不适合全部焊死在数据库层。

不串的关键在于：任何一次检索，tenant_id 必须由数据库身份上下文注入，而不是由调用方作为参数传入。一旦 tenant_id 是查询参数，漏传、传错、被提示注入篡改都只是时间问题。

### 2. 写入打标签、检索过滤还是物理分库：三层都要，但责任不同；漏掉存储层强制 = 串数据

腾讯云那篇 RAG 实践里有一个精准的判断：后置过滤比完全不过滤更危险，因为它制造了“已经隔离”的错觉，让越权数据在内存和日志中真实存在过，同时把本租户的文档挤出 TopK，风险从显性变成隐性。

所以正确的顺序是：写入时固化标签 → 检索时应用层过滤作为第一道 → 存储层强制作为不可绕过的兜底。adk-memshield 的设计是这一思路的典型：它把所有权门控从应用代码移入 PostgreSQL，使用 FORCE ROW LEVEL SECURITY 和事务级身份变量；漏传过滤条件的查询返回 0 行，而不是别人的行，并且连接池切换时身份不会残留。

只靠应用层 WHERE 过滤、没有存储层强制，是“哪层漏了会串数据”的答案：漏在检索路径上的任何一条查询、任何一个新功能、任何一次重构，而系统在事故发生时看起来完全健康。

### 3. 多设备：默认按用户共享，但用“读/写 scope 分离”和设备信任等级来划分体验与安全

默认应该按用户共享跨会话记忆，而不是按设备隔离。理由是记忆的核心价值在于“同一个人在不同设备上获得连贯体验”；按设备隔离会让用户在手机和 PC 上面对两个割裂的 Agent，体验退化严重。nautilus-compass 的设计原话就是“每个用户一个记忆空间，其在所有设备上的所有 agent 汇入同一空间；用户之间完全隔离”。

但共享不等于所有设备同权。可行的分层是：

- 个人可信设备：完整读写该用户的私有记忆。
- 低信任设备或共享设备：只读或临时会话，写回的记忆需要标记来源设备，或延迟合并、需要用户二次确认。
- 设备指纹本身不上传或只上传哈希/派生标识，避免把设备标识变成跨站追踪向量。

安全风险在于：如果共享设备上登录了同一账号，Agent 可能把该设备上的敏感查询写入用户级记忆，随后在用户的主设备上被召回。缓解手段不是退回设备隔离，而是在写入侧引入写入来源的信任等级，让低信任来源的记忆进入“待确认”或“仅本设备可见”的暂存层，而不是直接进入用户主记忆池。

### 4. 只靠 metadata 过滤不够；Embedding 本身会泄露其他用户的信息

不够，而且 embedding 的反演风险是真实的。

有两个被工程直觉误导的判断需要纠正：

1. “向量化了就匿名了” ——不成立。已有多项研究表明，文本 embedding 可以被反演回近似原文，包括 PII。OWASP 的 LLM 风险清单也将 embedding inversion 列为向量与嵌入的核心弱点之一，攻击者可以通过对配置不当的向量库发起 k-NN 查询来近似重建原始文档。
1. “按用户过滤了就隔离了” ——也不完全成立。检索是按相似度排序的，不是按权限排序的。如果 ACL 配在检索之后，最相关的私有 chunk 可能来自其他租户；在 pooled vector store 上做相似度搜索，即使没有任何“攻击”，也可能自然地把其他用户的记忆 surfaced 出来。

所以结论是：metadata 过滤是必要的，但不构成物理隔离；它只能作为“第二道门”，不能作为唯一门。对高敏感记忆，存储层的 namespace 隔离、独立 shard 或 RLS 是必须的；同时要假设“一旦向量本身泄露，内容就可能被还原”，因此不要把敏感原文的 embedding 放进低信任或共享的向量池。

### 5. 身份中途变更：归属旧用户，旧会话冻结；新会话按新身份重新投影

记忆的归属应该绑定到“写入那一刻”的身份，而不是“读取那一刻”的身份。

身份切换的常见失败模式已经被命名：identity drift——模型在同一会话中服务多个用户或人格时，混淆用户特定状态、跨角色泄露信息；切换越频繁，退化越明显，即使回复看起来仍然流畅。

工程上的正确边界是：

- 旧会话继续固定原身份和工作区，切换默认连接只影响新会话。
- 每一轮新会话按当前身份重新投影工具、知识和规则；user_id、tenant_id 不由模型自由填写。
- 记忆记录在写入时固化不可变的 owner_id（及 owner_kind），后续的“重新归属”必须是显式的管理操作，而不是隐式跟随当前登录态漂移。

“切换窗口”的处理原则是：切换动作本身是一个事务边界。切换前的所有写入归属旧用户；切换后的新会话从空白的身份上下文开始，不继承旧会话的工作记忆。如果产品上需要“代操作”，代操作产生的记忆应归属被代操作的目标用户（如果语义上是代表该用户执行），并同时记录操作者是代操作者，形成双主体溯源；但绝不能把代操作者在旧身份下产生的私有记忆静默带入新身份。
