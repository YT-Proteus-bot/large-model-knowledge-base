### 1. LLM 应用和传统后端服务在架构上最核心的差异是什么？哪些传统设计模式会失效？

**最核心的差异是：**传统后端执行确定性逻辑，LLM 应用执行概率性生成。传统模式假设“输入 A 必然得到输出 B、接口稳定、副作用有界”，而 LLM 引入的是“同一输入可能得到不同输出、延迟和成本随输出长度剧烈波动、模型行为可能漂移”。这个差异让四种传统模式失效。

- **第一，**同步请求-响应。 传统 API 毫秒级返回，LLM 生成可能数秒到数十秒。同步等待会占死线程和连接，而 LLM 的 P99 延迟可能是 P50 的数倍，固定超时要么误杀慢但正确的请求，要么设得太长拖垮上游。必须改为流式输出 + 异步编排，让用户先看到“正在生成”，而不是死等完整结果。
- **第二，**“重试即幂等”的假设。 传统幂等接口重试安全；LLM 调用重试会产生不同的输出（概率性），而如果输出触发了副作用（写库、发消息），重试就可能重复执行。更隐蔽的是，在 Agent 循环中，模型可能把一次失败“解释”成“需要重试”，然后继续调用工具，把一个小错误放大成循环错误和成本错误。必须把 LLM 调用的重试和副作用的幂等分成两个独立层：前者只负责拿到一个可用的生成结果，后者用幂等键保证写操作不重复。
- **第三，**无状态水平扩展。 传统无状态服务加机器就能扩；LLM 应用的瓶颈在模型供应商的配额（RPM/TPM）和上下文窗口，加机器不增加配额，反而可能因并发增加而触发 429。扩展必须从“加实例”转向“限流、降级、多供应商分流”，并用信号量而不是线程池来约束下游并发。
- **第四**，固定超时 + 失败即降级。 LLM 的延迟分布长尾很重，固定超时要么在正常波动时误杀，要么在长尾时毫无意义。必须按任务类型和输出长度设分级超时，并配合流式心跳判断“还活着”，而不是用一个全局值一刀切。

### 2. 完整链路包含哪些环节？哪一段最容易成为延迟和成本瓶颈？

一次 LLM 请求的延迟可分解为四个不可约部分：LLM 推理延迟（含 prefill 和 decode）、工具 I/O 延迟、沙箱/代码执行延迟、编排器开销。瓶颈的答案取决于你问的是“单请求延迟”还是“系统吞吐”——两者由不同的阶段主导。

对单请求延迟，瓶颈是输出 token 的数量（decode 阶段）。 有基准测试明确指出，延迟“对生成 token 的数量最为敏感”，自回归解码阶段是单请求计算成本的主要驱动因素。decode 是逐 token 顺序生成的，每 token 都受内存带宽限制，输出越长，总生成时间线性增长。这就是为什么聊天场景要精简回复、限制输出长度——输出是延迟的直接乘数。

对系统吞吐，瓶颈是输入 prompt 的长度（prefill 阶段）。 同一份基准的结论是：“输出 token 生成决定了单个请求的时长，但输入 prompt 的长度是系统吞吐的主要瓶颈”。prefill 是对整个输入做一次前向传播，计算密集；长上下文请求的 prefill 会“垄断资源，严重限制新请求的准入速率”。这意味着 RAG/长上下文场景的优化方向不是“让模型少说”，而是“让输入更短、更准”——检索精度和上下文压缩是主要杠杆。

一个容易被忽略的量化事实：每个输入 token 大约增加 0.24ms 的 TTFT P95；而每个缓存命中的输入 token 节省约 0.15ms 的 prefill，缓存 1000 tokens 约节省 100ms TTFT。这解释了为什么 prompt caching 对长系统提示或固定 RAG 模板是显著的延迟优化——它不是“让模型变快”，而是“让 prefill 跳过已计算的部分”。

成本方面，输出 token 通常比输入 token 贵 4–8 倍，因为 prefill 是可并行化的批量操作，decode 是顺序的、更慢的。但最容易失控的成本不是“一次调用”，而是 Agent 循环中的多次调用和长上下文反复注入——轮次越多，每一轮都重新 prefill 一次（除非有缓存），成本随轮次线性叠加。

### 3. Prompt 工程和应用代码的边界怎么划？哪些逻辑该写进 Prompt，哪些必须由代码控制？

边界判据是“确定性要求”：必须确定性、可测试、可审计、可重复的逻辑，归代码；语言驱动的、概率性的、需要语义理解的任务，归 Prompt/模型。一个简洁的表述是：代码编排器是确定性的骨架——工作流、状态、上下文、工具、协调；LLM 是推理肌肉——理解、创造、判断、解决问题。

必须由代码控制的：

- 业务规则、策略和授权检查（谁能做什么、金额上限、状态机转换）。
- 校验（格式、业务合法性）、错误处理、重试/超时、限流。
- 数据访问、合规控制、任何可能产生副作用的操作（写库、支付、发消息）。
- 契约和 SLA 的强制执行；风控和审计。

适合放进 Prompt 的：

- 摘要、提取、分类、改写。
- 基于检索上下文的推理。
- 当工具选择是模糊的，让模型决定“下一步调用哪个工具”。
- 语气、格式、角色的描述；任务的约束说明（“只输出 JSON”“不要编造不在上下文中的事实”）。

一个常见的错误是把业务规则写进 Prompt（“如果金额大于 1000 则拒绝”）。这有三个问题：模型可能忽略、可能被注入绕过、无法审计和复现。正确的分层是：代码先做硬校验，Prompt 只描述“任务是什么、输出格式是什么、约束是什么” ——校验逻辑不在 Prompt 里，而在模型输出之后的代码层。OWASP 的立场更直接：把模型输出当作不可信输入，是输出格式强制执行最重要的单一原则。Prompt 不拥有“决定权”，只拥有“生成权”。

### 4. 多轮对话的上下文窗口管理怎么做？截断、摘要、检索三种策略分别适合什么场景？

实际生产系统的优先级不是“三选一”，而是分层的：先做零 LLM 成本的无损/低成本压缩（observation masking、滑动窗口），再做有损的结构化摘要，检索作为跨会话的补充而不是会话内压缩的替代，截断是兜底而不是首选。

第一层：零 LLM 成本的确定性压缩（优先）。 Agent 轨迹膨胀的主要来源不是“对话轮次”，而是工具输出的冗长和噪声——一次文件读取、一次测试运行就可能产生数千 token。Observation masking 的做法是把旧的工具输出替换为结构化占位符（保留工具名和关键状态，删除大段返回内容），而不是让 LLM 去“总结”它。JetBrains 在 SWE-bench 上的系统对照发现：observation masking 在约 52% 的 token 成本下，匹配甚至有时略超 LLM 摘要的解决率，且零额外 API 调用。混合方法（先 masking，必要时再摘要）可以进一步降低成本 7–11%。这意味着一个反直觉的结论：“简单地把旧工具结果遮掉”比“让模型生成摘要”更划算，因为摘要本身要消耗 token、引入延迟，还可能丢失关键细节、拉长轨迹。

第二层：结构化摘要（有 LLM 成本，当旧上下文仍然重要时使用）。 主流框架收敛到的模式是：保留最近消息原文，把更早的消息摘要为一段“运行摘要”前置到对话中。摘要应该锚定式、分节（目标、已完成、待办、关键约束），而不是生成一段自由文本，因为结构化摘要保留的有用信息更多。触发条件按 token 数或消息数，而不是固定轮数。

第三层：检索（跨会话/长期记忆）。 检索不是“会话内压缩”的替代。如果当前会话的上下文窗口已经装不下，检索只是把“最相关的旧片段”重新拉回来，它不解决“窗口本身有限”的问题。检索适合跨会话的长期记忆（用户偏好、历史事实），不适合“当前会话内必须逐字保留的推理链”。

第四层：截断（兜底）。 当所有策略都失败或成本不可接受时，硬截断保证请求不爆。截断是最后手段，因为它丢失信息且不可逆。

关键原则：先清工具结果再摘要。 工具输出是上下文膨胀的主要来源，且工具结果可以按需重新获取；摘要是有损的，应该在零成本策略不够用时才使用。

### 5. 结构化输出怎么保证可靠性？JSON Schema 约束和代码校验分别负责什么？

JSON Schema 约束负责“语法和结构合法性”（是不是合法 JSON、字段是否存在、类型是否正确、枚举是否在范围内）；代码校验负责“业务合法性”（日期是否早于今天、库存是否足够、状态机是否允许、权限是否匹配）。两者都不能单独保证可靠性，必须叠成五层防线：输出约束 → 语法解析 → Schema 校验 → 业务校验 → 失败处置。

约束解码能做什么、不能做什么：生产 serving 框架上的 guided decoding 已经把 JSON 合规性从无约束的 61–94% 提升到 96–100%，且 XGrammar/llguidance 这类引擎的开销接近零（约 50 微秒 CPU/token）。这解决的是“模型吐出非法 JSON”的问题。但 Schema 不能表达业务规则：due_date 是合法的 ISO 日期，但可能是 2020 年；priority 是合法枚举，但业务上这个工单不允许设为 urgent；金额是合法数字，但超过了账户余额。“合法 JSON 不代表字段正确，字段正确不代表业务允许。”
