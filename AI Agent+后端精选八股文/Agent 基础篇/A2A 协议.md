#### 1. MCP 协议和 A2A 协议如何协同工作？请设计一个同时使用两者的多 Agent 系统架构。

MCP 和 A2A 的关系是纵向与横向的分层互补，不是竞争或替代。MCP 处理 Agent 向下的能力接入，A2A 处理 Agent 之间的对等协作。Google 的比喻是：A2A 是 horizontal bus，MCP 是 vertical bus。一个典型的生产架构中，Orchestrator Agent 通过 A2A 把任务委派给 Specialist Agent，后者内部通过 MCP 调用数据库、API、文件系统等工具。

**一个同时使用两者的多 Agent 系统可以按四层设计：**

- 编排层（A2A 横向） ：主控 Agent 承接目标，拆分子任务，通过 A2A 把任务委派给专业 Agent。A2A 负责 Agent 发现（Agent Card）、Task 生命周期（submitted → working → completed）、跨运行时委托和结果回传。编排层不直接调用工具，只管理“谁来做、做到哪了、结果是否被接受”。
- 专业 Agent 层（A2A 对等节点） ：每个专业 Agent 是一个独立的 A2A 服务端，通过 Agent Card 声明自己的能力边界和认证要求。它接收 A2A Task，内部完成推理，通过 MCP 调用所需工具，最终把结果作为 A2A Artifact 返回。
- MCP 能力接入层（纵向） ：每个专业 Agent 只连接自己完成任务所需的 MCP Server，工具权限按角色收窄。一个 Agent 不应持有与它无关的工具凭据。MCP 负责工具发现、调用、上下文注入和结果回传。
- 治理与观测层：身份认证、委托链管理、任务级授权、幂等、超时、循环终止、审计 Trace 和人工审批。这一层不属于 MCP 或 A2A 协议本身，但它是让两者协同后不失控的前提。

关键分工：A2A 不传递工具调用细节，MCP 不参与 Agent 间协商。A2A 的 Task 对调用方是不透明的，远程 Agent 内部用什么 MCP 工具、什么模型，调用方不需要知道；MCP 的工具调用发生在单个 Agent 的上下文内，不跨越 Agent 边界。

#### 2. A2A 协议中的 Agent Card 是什么？它在多 Agent 发现和协作中起什么作用？Agent Card 能否替代权限系统？公开 Agent Card 有什么安全风险？

Agent Card 是 A2A 的发现入口，是一个发布在 /.well-known/agent-card.json 的 JSON 元数据文档，描述 Agent 的身份、endpoint、skills、支持的接口、streaming 能力、所需的安全 schema 和版本。调用方在发起任何委托之前先获取 Agent Card，判断“这个 Agent 能做什么、怎么调用、需要什么认证”。

它在发现和协作中的作用是候选筛选和契约前置：编排层不应该靠自由文本猜测谁有能力，而应该基于 skills 和 capabilities 做确定性的候选过滤；调用方在发送 Task 之前就知道目标 Agent 的输入输出模态和认证要求，减少无效调用和事后失败。

Agent Card 不能替代权限系统，A2A 协议本身也故意把授权排除在外。 v1.0.0 的设计明确将 authorization 留给外部基础设施，Agent Card 中的 securitySchemes 描述的是认证要求，不是授权决策。JWS 签名可以验证“这张卡是否由声称的域名签发”，但它验证的是卡片的发布者身份，不验证“当前这次委托在什么 scope 下、代表谁执行”。A2A 甚至没有在 payload 中携带身份信息，每个请求必须在 HTTP 层单独认证。真正的权限判定必须由独立的授权系统基于调用者身份、委托链、scope 和资源归属来完成。

公开 Agent Card 的安全风险集中在发现阶段的攻击面。Agent Card 包含攻击者可控制的自然语言字段（描述、技能说明），这些字段在调用发生之前就可能影响编排层的 Agent 选择，形成预调用信任问题。具体风险包括：在描述中植入诱导性文本影响 Agent 选择；通过技能说明泄露内部能力边界；用虚假 capabilities 诱导调用方发送超出实际授权范围的请求；以及卡片本身被篡改或冒用。此外，Agent Card 绝不能包含 API key、bearer token、client secret 或私钥，凭据的获取必须走带外流程，敏感卡片应受保护而不是内嵌秘密。对公开 Registry 中的卡片，必须验证签名，并且只接受未过期、未被撤销的密钥，而不是盲目信任卡片的声明。

#### 3. A2A 协议的核心原理是什么？

A2A 的核心是以 Task 为中心的状态化远程协作，而不是自由对话。

- 发现：通过 Agent Card 在委托之前完成能力发现和契约匹配，而不是靠运行时的自然语言协商。
- Task 是基本协作单元：Task 有明确的目标和 executor，包含 task_id、context_id（跨 Agent 的上下文管理）、状态和 Artifact。Task 的生命周期是显式的状态机（submitted → working → completed / failed / cancelled，以及 input_required 等中断状态）。状态由服务端记录，不由模型自行声称“已完成”。
- 消息与 Artifact 分离：Message 是 Task 内的对话轮次，Artifact 是 Task 的最终输出。调用方消费的是结构化的 Artifact，而不是一段自由文本。
- 异步优先：A2A 支持长任务，调用方可以先获得 task_id，再通过查询或订阅获取进展和结果，而不是同步阻塞等待。
- 不透明执行：A2A 不要求远程 Agent 暴露内部工具链、记忆或推理过程。远程 Agent 内部通过 MCP 调什么工具，调用方不需要知道，也不应该依赖。

A2A 解决的是“Agent 之间怎么发现、怎么委托、怎么追踪状态”，它不解决权限委托、多跳信任和工具调用——那些由独立的信任层和 MCP 层承担。

#### 4. 你们这个 A2A 协议实现了什么？为什么没有直接使用官方实现？你们自己实现的有什么区别？

需要先澄清一个前提：“不用官方实现”通常不是拒绝 A2A 协议本身，而是在协议层对齐标准的同时，保留工程层的控制权。 官方 A2A 提供了多语言 SDK（Python、JS、Java、Go、.NET），但 SDK 的成熟度、依赖和生命周期假设未必匹配具体工程的边界条件。

自研实现通常覆盖：Task 的提交、查询和状态流转；Agent Card 的获取、缓存和签名校验；JSON-RPC 请求/响应封装和错误映射；幂等键、超时和重试；以及与内部任务存储、审计和事件总线的对接。

与官方 SDK 的主要区别集中在几个工程判断上：

- 生命周期单元的匹配。官方或第三方 A2A 桥接库可能假设“一个进程对应一个 Agent 会话，桥接随会话退出”，而工程需要的可能是“一个持久化服务监督多个长期运行的 Agent worker”。生命周期单元不一致时，直接嵌入 SDK 的代价高于自己实现一个薄层。
- 完成语义的控制权。某些现成实现允许 Agent 自行把 Task 标记为 COMPLETED，而生产系统需要的信任模型可能是“完成由编排器验证证据后裁定，绝不由 Agent 自称”。这不是参数调整，而是状态机所有权的反转，复用现成库意味着重写状态机而不是复用。
- 持久化和恢复的自主性。如果系统已经有一个统一的数据库或状态存储，自研可以让 Task 和 Message 日志直接落在现有存储中，而不是引入一个带自己 TTL 和内存 map 的额外存储层，再在其上叠加重试和持久化。
- 依赖和平台约束。官方 SDK 可能引入特定的序列化、运行时版本或平台依赖。如果目标环境（如 Android、特定 JVM 版本或受限的依赖树）尚未验证这些依赖，自研一个只依赖最小协议原语的实现，是更可控的工程选择。

一句话：自研的是“A2A 协议语义的一个受控子集”，协议形状对齐标准以保证互操作，工程语义按内部信任模型和生命周期重新实现。

#### 5. A2A 协议和你的项目场景匹配度如何？

匹配度取决于项目是否存在跨服务边界、由不同运行时或团队实现的 Agent 协作，而不仅仅是“有多个 Agent”。

如果系统是单 Agent + 多工具，MCP 就够了，引入 A2A 是过度设计——它增加了 Task 状态管理、Agent 发现和跨运行时协调的开销，却没有对应的协作收益。A2A 匹配的场景是：多个专业 Agent 需要在不硬编码连接的情况下互相发现、委托任务、追踪状态和回传结果，尤其是跨组织、跨 vendor 或跨团队的场景。

在匹配的场景中，A2A 的价值是把 Agent 协作从自然语言传递升级为结构化任务契约：task_id、幂等键、deadline、显式状态机替代了“把一段话塞进对方上下文、再等一段话回来”的松散模式。长任务可以先拿 task_id 再异步查询，而不是同步阻塞或轮询聊天历史。

不匹配的边界同样重要：A2A 不替代身份认证、权限管理、消息队列和审计平台。如果项目把这些能力寄托在 A2A 协议本身，匹配度会很高但落地会失败。A2A 只定义协作契约，不定义信任和治理；多跳委托中的权限衰减、任务级授权和审计必须由项目自己的基础设施补齐。

#### 6. 如何防止多 Agent 互相 A2A 停不下来？

A2A 的 peer-to-peer 模型天然存在循环风险，仅靠“最大调用深度”不够——A → B → A 的深度只有 2，任何合理的深度上限都不会拦住它。

有效的防护是分层约束，而不是单一阈值：

- 深度与访问集双重检查。每个 Task 携带调用链上下文，在分发前同时检查当前深度是否超限，以及目标 Agent 是否已在本次任务的 visited_agents 中。访问集检测能拦住短链路回环，深度限制能拦住长链路递归，两者互补。确实需要回访的合法模式（例如所有 Agent 都要经过的记忆 Agent）通过显式白名单放行，而不是全局关闭检查。
- 任务级预算，而不是单 Agent 预算。每个根任务维护跨所有 Agent 的共享预算——总步数、总 Token、总工具调用次数、总耗时。单个 Agent 内部的循环可能被它自己的限制拦住，但多个 Agent 之间“每个都只走几步”的协作循环不会被单 Agent 预算捕获，必须把预算提升到任务树层面，任一维度耗尽就终止整棵任务树。预算必须在下一次 API 调用之前强制执行，而不是事后对账。
