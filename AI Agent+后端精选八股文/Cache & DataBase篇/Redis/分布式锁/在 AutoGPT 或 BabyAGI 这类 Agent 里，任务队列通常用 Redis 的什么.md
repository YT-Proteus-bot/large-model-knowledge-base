# 在 AutoGPT 或 BabyAGI 这类 Agent 里，任务队列通常用 Redis 的什么数据结构？

> 原文：https://lcnipys9u0xh.feishu.cn/wiki/IlgswCjCricUC3kbgJyc9Y70nWd

“这要分场景，不是一种结构打天下。自主 Agent 的任务队列其实有两个维度：按顺序执行的简单任务队列用 Redis 的 List，带优先级或延迟执行的任务队列用 ZSet。实际框架里通常是两者组合，甚至同一套系统里两条队列并存。

一、顺序任务队列：List

BabyAGI 这类 Agent 把大目标拆成一系列子任务，这些子任务天然有先后依赖——‘查天气’必须在‘穿衣建议’之前完成。这种先进先出的顺序队列用 Redis 的 List 最直接：

- 生产者用 RPUSH task:queue '{"taskId":"t1","action":"weather"}' 把任务塞到队尾。
- 消费者用 BLPOP task:queue 0 阻塞式地等，队头出一个任务执行。
- 简单、可靠，而且 BLPOP 天然支持多消费者抢单，谁抢到谁执行。

但它的局限是不支持优先级，所有任务一视同仁。当 Agent 想在中途插入一个紧急任务（比如用户突然说“先别订酒店了，帮我改签航班”），List 很难优雅处理，只能塞到队尾，等前面的跑完。

二、优先级 / 延迟任务队列：ZSet

AutoGPT 这类 Agent 更复杂，任务不仅有多级优先级，还经常要延迟执行——比如‘等支付确认后再发电子发票’，或者‘5 分钟后重试失败的搜索’。这种场景下 ZSet 是标准答案：

- member 存任务 JSON。
- score 存优先级数值或执行时间戳。如果 score 是优先级（越小越优先），消费者每次 ZPOPMIN 取优先级最高的任务；如果 score 是执行时间戳，消费者用 ZRANGEBYSCORE 0 NOW LIMIT 0 1 取出到期的延迟任务。
- 配合 Lua 脚本可以原子化出队，避免多 Agent 争抢同一个任务。
- ZSet 天然支持按优先级排序和按时间范围查询，比 List 灵活得多。

AutoGPT 的任务队列通常就是一个大 ZSet，score 用来做任务排序，紧急任务优先级更高，新拆解出的子任务优先级次之，周期性巡检任务靠后。消费者用 ZPOPMIN 无脑抢最高优先级任务即可。

三、复合设计：List 跑串行，ZSet 做调度

实际生产环境里，我通常不会二选一，而是把两者结合：

- 一个执行队列用 List，它只存已经就绪的任务，消费者们直接 BLPOP 快速抢单执行，不走优先级判断。
- 一个调度队列用 ZSet，它存所有待排期的任务，score 是执行时间戳或优先级，由一个轻量的调度器 Agent 定时从 ZSet 里捞到期任务，拆成可执行单元塞到 List 里。

这样做的好处是把调度和执行解耦——调度器负责规划‘什么任务在什么时候该运行’，执行集群只负责无脑抢 List 干活。对延迟和优先级的要求全部在 ZSet 层处理，List 层就保持极简和极高的消费速度。

四、辅助结构：去重和状态管理

光队列还不够，Agent 任务还有去重需求（同一个目标不要重复拆解），通常再加一个 Set 存已处理的任务 ID，或者用 Redis 的 Hash 存任务状态（待执行、执行中、已完成、失败），ZSet/List 只存任务 ID，取到后再 Hash 里读详情。这样任务状态和队列分离，更新状态不影响队列结构。
