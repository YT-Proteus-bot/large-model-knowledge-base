#  Redis 的大 Key 问题，在 Agent 对话历史存储中常见吗？

> 原文：https://lcnipys9u0xh.feishu.cn/wiki/NhmZwbJRCiQT5Bk6OpbcsC6Tnsg

“非常常见，对话历史简直是大 Key 的温床。Agent 的多轮对话本质上是持续追加的单向数据流，如果直接用 Redis 的 List 或 ZSet 存储一个会话的全部消息，不做长度控制，几十轮对话下来轻轻松松几 MB 甚至几十 MB，再高并发下就是灾难。所以这不是可不可能的问题，而是早晚会撞上的问题。

一、为什么对话历史容易成大 Key？

一个会话的对话历史通常有两种存法：

- List：lpush session:abc123:messages "role:user|content:..."，每次都往头部塞。
- ZSet：zadd session:abc123:messages timestamp "..."，以时间戳做 score。

无论哪种，本质都是无限追加。假设平均每条消息 200 字节，20 轮就是 4KB，看起来还好。但 Agent 的会话可能持续几个小时甚至几天，加上 Skill 返回的结构化数据、长文本摘要，一条消息就可能达到几 KB。100 轮对话后单 Key 达到 500KB 到数 MB 并不少见。Redis 是单线程处理命令，一个大 Key 的读取（比如 LRANGE 0 -1 取全部历史）会直接阻塞其他请求，造成延迟毛刺。

二、大 Key 的连锁反应

- 网络带宽打满：一个 10MB 的 Key 取一次，占用带宽不说，序列化/反序列化也吃 CPU。
- 内存碎片：频繁追加和删除会导致 Redis 内存碎片，大 Key 一旦需要扩容或删除，DEL 操作会阻塞 Redis 主线程几秒甚至更久，线上直接卡死。
- 主从同步延迟：大 Key 的写入会瞬间推高主从复制缓冲区，造成从节点延迟飙升。

三、Agent 场景下的特殊放大

Agent 的记忆不仅包括用户和 Agent 的对话，还经常嵌入检索到的知识片段、Skill 返回的 JSON 结果、工具调用链。这些数据的体积远超普通聊天，比如一个航班查询结果可能就包含几十个航班的详细信息。如果把这些全存进一个对话历史 Key，大 Key 几乎是必然的。

四、我们的治理方案

我们主要从四个方面避免：

1. 强制截断 + 滚动窗口：对话历史只保留最近 N 轮（比如最近 20 条消息）。用 LTRIM 命令在每次追加后裁剪，或者用 ZSet 的 ZREMRANGEBYRANK 保留最近 N 条。LLM 的上下文窗口本来就有限，保留全部历史没意义。
1. 分离存储：对话元数据 vs 消息详情：对话的标题、状态、参与者等元数据用 Hash 存，轻量且字段独立。消息历史存在专门的 List/ZSet 中，并且拆分——长消息的完整内容放在对象存储或独立的 String Key 里，对话历史只存消息 ID 和摘要。这样主 List 只存元指针，体积小得多。
1. 数据压缩：对消息体做 gzip 压缩后再存入 Redis，虽然消耗一点 CPU，但能将体积缩到原来的 1/5 到 1/10。这个我们用于历史归档的对话，实时对话不走压缩以保证速度。
1. 设置严格的 TTL：对话历史 Key 必须设过期时间，比如 30 分钟或 24 小时，根据业务需要。过期后 Redis 自动清理，不积累无用的长对话。
1. 监控告警：用 redis-cli --bigkeys 或 MEMORY USAGE 定期扫描大 Key，对超过 100KB 的 List/ZSet 主动告警，触发人工或自动拆分。

五、如果不治理会怎样？

我曾经遇到一个线上故障：某测试 Agent 的对话 Key 积压到 200MB，运维执行 KEYS * 时顺带把它读了出来，导致 Redis CPU 100% 堵塞了 4 秒，期间所有 Agent 心跳超时，大量任务被误判失败。这是血淋淋的教训。
