# 87.大模型（LLMs）文档解析（PDF, OCR）

> 原文：https://lcnipys9u0xh.feishu.cn/wiki/Ag8Qw4DUZiuEEGkvxB4ctXp7nQy

#### 1. 为什么 PDF 解析是 RAG 系统的难点之一？PDF 文件有哪些常见的解析陷阱？

PDF 解析是 RAG 流程中最棘手、最容易出现质量问题的环节之一。根本原因在于 PDF 是一种展示格式，而非结构化文档格式。它的设计初衷是保证无论在何种设备、何种系统上打开，文档的视觉效果都一致，因此它记录的是“在页面的某个坐标绘制某个字符或图形”的指令流，而几乎不保留任何关于文本逻辑结构的信息，如段落、标题、阅读顺序和表格结构。

常见解析陷阱：

1. 文本提取为乱码或不可读字符：这是最臭名昭著的问题。某些 PDF 生成器为了压缩体积或使用特定字体，会将字符映射为非标准的编码。解析器如果无法正确匹配编码与字形，提取出来的文本就成了乱码。另一个常见情况是 PDF 中的文字被转换为轮廓曲线，此时文本已不再是“字符”，而是“图形”，任何文本解析工具都会直接失效，只能求助于 OCR。
1. 阅读顺序混乱：这是处理多栏排版时最典型的陷阱。人类阅读时，视线会自然地在栏与栏之间切换，但 PDF 解析器只是按生成指令的顺序提取文本。它可能会从左栏的第一行开始，直接跳到右栏的第一行，将两栏的内容交织在一起，产生完全无法理解的乱序文本。当文档中穿插表格、图片、侧边栏时，这种问题会更严重。
1. 段落、句子被意外截断：PDF 文件的每一页、每一行文本常常是独立绘制的。解析器提取文本后，往往会保留这些物理换行。一个原本完整的段落，可能因为每行末尾的换行符而被切分成大量短行。如果不做后处理，这些断行会破坏语义的连贯性，导致下游的分块和嵌入质量急剧下降。
1. 页眉、页脚、页码和脚注混入正文：这些元素在每页重复出现，但并非正文内容。简单的解析器会将它们与正文一起提取出来，穿插在文档的各个地方，引入大量噪音。这使得检索系统可能因为这些重复的无关信息而做出错误匹配。
1. 表格和图表信息丢失或变形：PDF 中的表格通常由水平的线条和独立的文本块拼凑而成，缺乏“行”和“列”的逻辑概念。解析工具可能把表格中的每个单元格单独提取，打乱原有的行列关系。图表则常常完全被忽略，或者只提取出其中零散的坐标轴标签。
1. 双重文本层问题：一些扫描件 PDF 会包含两层数据：底层是扫描得到的图像，上层是经 OCR 后添加的透明文字。如果解析器不加区分地同时提取这两层，就会得到重复的内容。更糟糕的是，如果 OCR 结果本身存在错误，它反而可能污染原本准确的文本层。

因此，在 RAG 系统中，PDF 解析绝不是简单地调用一个开源库的默认函数，而是需要针对具体文档的生成方式、排版特点和内容类型，组合多种技术和启发式规则，进行定制化的预处理和后处理。

#### 2. 比较几种常见 PDF 解析工具（PyMuPDF, pdfplumber, PDFMiner）的适用场景和优劣。

在 Python 生态中，PyMuPDF、pdfplumber 和 PDFMiner 是三个最主流的 PDF 解析库。它们在设计哲学、性能、解析深度和易用性上各有侧重。

- PyMuPDF (fitz)：它是一个高速、功能丰富的库。其底层基于高性能的 C 语言库 MuPDF，因此在处理大型文档时速度极快，这是它最大的优势。它不仅可以提取文本，还能以简单的方法获取文本的精确坐标、字体和大小等布局信息。它的文本提取方式非常灵活，支持“文本块”模式，能够将空间上邻近的文本行自动分组，对保持阅读顺序有一定帮助。它还能直接渲染页面为图像，为 OCR 管道提供输入。但它是一个商业友好的开源库（AGPL），在解析某些复杂排版时，其粗粒度的文本块分组可能不如基于规则的精细处理方法精确。
- pdfplumber：这是一个在表格提取和数据挖掘领域表现出色的库。它的设计哲学非常友好，每页被建模为一个包含字符、线条、矩形等对象的画布。开发者可以轻松访问这些对象的属性（坐标、文本、宽度），从而实现高度定制化的解析逻辑。它对表格的支持极佳，内置的表格提取算法能通过分析线条和文本位置，将表格转换为结构化的列表或 DataFrame。但它处理大型文档的速度较慢，因为它保留了过多的对象细节。
- PDFMiner.six：这是较老的库 PDFMiner 的维护分支，是纯 Python 实现的。它最大的价值在于提供了对 PDF 内部结构的低级访问。你可以遍历页面上的每一个 LTTextBox、LTChar 等对象，并获取它们的精确位置和属性。这让开发者可以实现任何复杂的自定义解析逻辑，例如精细控制多栏文本的排序。但它的 API 相对复杂，使用门槛较高，处理速度是三者中最慢的，通常不适用于需要高吞吐的实时应用。

适用场景与优劣总结：

- 追求速度和通用性：PyMuPDF 是首选。适合快速原型开发、对大量文档进行批量文本提取的场景。如果文档排版不是极端复杂，它通常能以最小的代码量获得良好的结果。
- 核心任务是提取表格：pdfplumber 是专门针对此场景优化的利器。它的表格提取能力在开源界首屈一指。适合财务报表、实验数据报告等富含表格文档的解析。
- 处理极端复杂排版或需要深度定制：当文档排版极其复杂（如杂乱的多栏、不规则图文混排），需要设计特定的切割和排序算法时，pdfplumber 或 PDFMiner 提供的细粒度对象访问能力就至关重要。它们让你能够“看见”并操纵页面上的每一个元素，从而编写专有的恢复逻辑。

在实际工程中，这些工具常常不是互斥的，而是互补的。一个常见的管道是：先用 PyMuPDF 快速提取简单部分的文本，对于检测到表格的区域，再专门调用 pdfplumber 进行精细解析。

#### 3. 如何从 PDF 中提取文本时保持阅读顺序？尤其是多栏排版、表格穿插时。

保持阅读顺序是 PDF 解析中最具挑战性的问题之一，因为原始的 PDF 指令流几乎不包含任何逻辑顺序信息。要解决这个问题，就需要模拟人类的阅读行为，利用文本片段的二维空间坐标来重建它们的正确顺序。

最有效的方法被称为“基于布局分析的排序算法”：

1. 获取带坐标的文本块：首先，使用 PyMuPDF 或 pdfplumber 等工具，不直接获取全文文本，而是提取页面上的所有文本片段，每个片段都包含其文本内容及其在页面上的边界框（Bounding Box，例如左上角和右下角的 x、y 坐标）。
1. 分组与聚合：将空间上邻近的文本行聚合成候选段落。可以设定一个合理的行间距阈值。这一步骤的目的是重建最基本的文本行，并将属于同一段落的连续短行初步合并。
1. 检测并隔离“干扰区”：在排序之前，最关键的一步是识别并暂时移除那些不属于正常文本流的区域，如表格、图片、侧边栏和页眉页脚。这通常通过分析块的尺寸、长宽比、或训练一个专门的布局分割模型来完成。将这些区域标记并移出排序序列。
1. 层次化排序：对剩余的主文本区域，实施一种模仿人类阅读的层次排序逻辑：
  - 自上而下，再自左而右。首先，将所有候选段落按其顶部的 y 坐标进行排序，分成不同的行。
  - 栏的检测：对于同一水平行上的文本块，检查它们是否属于不同的栏。这可以通过分析 x 坐标的分布来完成。如果文本块可以清晰地根据 x 坐标被分成几个聚集的群组，那么这些群组就是独立的“栏”。
  - 栏间排序：对栏从左到右进行排序。阅读顺序是先读完左栏的所有内容，再跳到右栏的开头。
  - 栏内排序：在每个栏的内部，文本块的顺序就是由上至下的自然顺序。
1. 回填特殊区域：在主要的文本流被正确排序后，根据文档的上下文或规则，将之前被隔离的表格、图片的标题等，插入到它们在文档中逻辑上所属的位置附近。

通过这种“空间分析 - 干扰隔离 - 层次化排序”的策略，即使面对复杂的多栏、表格穿插的 PDF，我们也能在很大程度上恢复出符合人类阅读习惯的文本顺序，为后续的 RAG 流程提供高质量的输入。

#### 4. OCR 在文档处理中的作用：什么情况下必须用 OCR？常用 OCR 引擎有哪些？

OCR 在文档处理中扮演着“最后的信息挖掘者”角色。当其他所有直接提取文本的方法都失效时，它就是唯一的希望。它将文档页面视为图像，通过计算机视觉和序列建模技术，将图片中的文字形状转换为机器可编辑的文本。

必须使用 OCR 的情况：

1. 扫描件或图片型 PDF：这是最典型的场景。文档由扫描仪或相机拍摄生成，每一页本质上都是一张图片，没有任何可提取的文本数据。
1. 文本已被转换为曲线或轮廓：某些 PDF 文件在生成时，出于设计或字体的原因，将文字转换为了矢量图形。对于解析器而言，页面上没有“字符”，只有“图形”。
1. 文本提取结果为乱码且无法修复：即使 PDF 有文本层，但如果其字符编码（CMap）被损坏或无法被正确映射，导致提取出的全是乱码，且没有其他可靠的方法修复，那么 OCR 就是唯一的补救措施。

常用 OCR 引擎：

- Tesseract：一个历史悠久、社区庞大的开源 OCR 引擎，由 Google 维护。它支持超过 100 种语言，使用 LSTM 神经网络进行识别。Tesseract 的优点是完全免费、离线可用、支持语言广。缺点是它对于图片质量的依赖较高，复杂布局的预处理（如倾斜校正、去噪）需要手动编码实现，识别带有艺术字体的文本效果不佳。
- PaddleOCR：由百度开源，近年来在性能和准确率上表现出色，尤其是在中文场景下。它提供了一个端到端的管道，不仅包含文本识别，还自带了强大的文本检测模型，能准确定位图片中的文字区域。它还内置了方向分类器，能自动纠正倒置或侧向的文字，对复杂排版有较强的适应性。
- 云服务 API：包括 Google Cloud Vision OCR、Amazon Textract、Azure Form Recognizer 以及国内的腾讯云 OCR、阿里云 OCR 等。这些云服务的优势是准确率极高，尤其是在处理复杂背景、模糊或强透视的文本时。它们往往能提供更多高级功能，如自动识别文档结构（表格、键值对）。缺点是它们是付费服务，需要网络连接，并且涉及数据隐私问题。

在实际的 RAG 管道中，通常的策略是“先提取，后 OCR”。先尝试用 PyMuPDF 等库提取文本，如果提取失败、结果为空或质量极低，再自动切换到 OCR 引擎进行识别。

#### 5. 在扫描件 PDF 中，如何结合 OCR 与布局分析来还原文档结构？

对于扫描件 PDF，我们的输入只是一张纯图片。要从中还原出带有结构信息的文本，不能简单地调用 OCR 提取一段冗长的文本，而必须将视觉布局分析与OCR 文字识别有机结合，形成一个从“看到”到“读懂”的完整管道。
