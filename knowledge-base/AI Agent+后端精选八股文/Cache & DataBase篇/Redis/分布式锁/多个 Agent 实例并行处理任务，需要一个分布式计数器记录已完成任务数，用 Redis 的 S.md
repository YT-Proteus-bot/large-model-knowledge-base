💡 我的决策逻辑：

“如果是纯粹的全局任务计数器，且没有拆维度的计划，我直接拍 String，用 INCR 命令。干净，零歧义。但如果我知道业务下一秒就会问‘能不能看下各个Agent完成的不同任务类型数量？’，那我会提前设计成 Hash，用 HINCRBY task:stats total 和 HINCRBY task:stats agent_a_done 一口气承载多维度计数。这叫为演进留钩子，不叫过度设计。”

### 二、原子自增的注意事项（全是坑点）

“因为 Redis 是单线程处理命令的，所以 INCR 和 HINCRBY 本身都是天然原子操作，并发多少个 Agent 进来都不会导致计数加错。这是 Redis 给我们的免费午餐。但真正容易出事的，是下边这四个被忽视的点。”

## 题2：🚫 严禁“先读后写”的假原子

“最经典的错误代码是：

```
current = redis.get("task:total")   # 读
redis.set("task:total", current + 1) # 写
```

这在并发下必然导致计数丢失。只要你的操作分成了两步，中间就一定有并发窗口。必须用 INCR 本身一步到位。”

## 题3：📜 复合操作必须用 Lua 脚本押送

“当原子自增后还要附带条件判断时（比如‘完成数超过1000就发通知，但只发一次’），就不能只靠一个 INCR 了。比如：

```
完成数 = INCR task:total
if 完成数 == 1000:
    发消息
```

并发时，两个 Agent 可能都让计数刚过 1000，导致消息发两次。正确的做法是把 INCR 和条件判断与消息发送逻辑，打包成一个 Lua 脚本传给 Redis 执行。 Lua 脚本在 Redis 里执行时整个阻塞其他命令，能保证这段逻辑的原子性。”

## 题4：🔥 热点 Key 问题与集群下的限制

“高并发 Agent 都去 INCR 同一个 Key，在 Redis 集群里，这个 Key 会固定在某个节点上，那个节点 CPU 就可能被打满。如果量级真的巨大，需要考虑本地计数+定时批量上报，或者在业务可接受的范围内，用分桶计数：比如 task:total:{1..10} 十个 Key，加一个定时任务去汇总。当然这会牺牲一点实时准确性，要权衡。”

## 题5：⏳ 持久化丢数与溢出

- 丢数风险：Redis 的 RDB 或 AOF 持久化在极端宕机时，可能丢失最后几秒的计数。如果你的计数器是计费依据，不能丢，那就要在业务层做额外的账本，Redis 只当缓存加速，不以它为准。
- 溢出：Redis 的整数是 64 位有符号长整型，上限是 9,223,372,036,854,775,807。一般任务计数撞不到，但心里得有这根弦。

### 面试收尾（选一个你喜欢的风格，每次不要重样）

结尾 A · 坦诚派（适合展现工程严谨性）

“坦白讲，这个选择特别典型：技术上用 String 就够了，但工程上我总会多问一句产品，确认未来不会加维度。因为一旦上线后要把 String 迁成 Hash，历史数据迁移和代码兼容都是债务。另外我还会坚持在计数器上线同时，就配上 INCR 调用的 P99 延迟监控，因为如果突然变慢，很可能就是热点 Key 在预警了。”

结尾 B · 深挖派（适合引导向你的长板）

“其实选择本身之外，我更关注这个计数器在业务失败时怎么处理。比如 Agent 完成任务但 INCR 成功了，后续写数据库却失败了，计数和实际就永远对不上了。所以我会把它放在一个本地事务消息里，或者借助 Redis Streams 做至少一次处理，保证计数的最终一致性。面试官您这边在处理这种‘命令成功但业务失败’的回滚时，一般倾向重试还是补偿？”

结尾 C · 简洁有力派（适合节奏快的面试）

“一句话总结我的做法：全局用 String，多维用 Hash，读写必原子，复杂上 Lua。 在实际项目里，我还会让计数器具备一定容错，因为任务计数往往是监控大盘的数据源，我会用冗余采集或上报中断自动恢复来防止单点数据缺失引发报警误报。”
