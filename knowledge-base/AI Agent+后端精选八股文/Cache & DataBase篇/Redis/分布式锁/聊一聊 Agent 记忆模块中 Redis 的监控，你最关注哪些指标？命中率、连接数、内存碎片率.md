Agent 的记忆模块对 Redis 的依赖，跟普通业务缓存还不太一样。记忆是 Agent 推理的上下文，如果 Redis 出问题，不是‘页面加载慢一点’，而是Agent 直接变蠢，因为它记不起之前说过什么了。所以我的监控会围绕一个核心循环来布点：请求进来了多少 → 读了/写了多少 → 消耗了多少资源 → 有没有异常卡住。我挑四个最关键的来说，顺带把这三个飙升场景拆开。”

## 二、命中率突然飙升（过山车式飙升，或是突然跳水）

这里要先分清是 “飙升到接近 100%” 还是 “从 90% 暴跌到 30%”，两者原因完全不同。

## 场景1：命中率突然飙到近乎 100%（不正常的健康）

“这往往不是好事，很可能是‘缓存变成字典’了。”

- 可能原因：过期策略失效或大量记忆 TTL 被误设为永久。Agent 记忆全堆在内存里从不淘汰，所有 key 都命中。但这会撑爆 Redis 内存，触发 OOM 或 maxmemory-policy 强制淘汰，瞬间又把命中率砸下来。
- Agent 特有原因：代码 Bug 导致记忆 EXPIRE 命令没执行成功；或者会话结束后的清理逻辑挂了，导致死会话堆积。
- 排查思路：立刻看 used_memory 曲线和 expired_keys 是否趋近于零，确认是不是“伪健康”。

## 场景2：命中率突然断崖式下跌

“这才更常见，也更要命。”

- 可能原因：
  1. 批量过期风暴：大量会话在相近时刻同时过期，Redis 主线程忙于删除过期键，正常请求被阻塞，新的记忆又没加载进来，命中率雪崩。
  1. 缓存被错误清空：某个管理脚本或 CI 流程执行了 FLUSHALL 或 FLUSHDB。
  1. 内存淘汰触发：maxmemory 到了，策略是 allkeys-lru 或 volatile-lru，大量有效记忆被驱赶，冷数据进来后命中率崩盘。
  1. 流量打偏：Agent 负载均衡策略变了，同一会话的请求被分配到不同 Redis 节点，本地无记忆又去查，等于全 miss。
- Agent 场景：如果 Agent 每次对话都依赖“用户偏好记忆”，命中率暴跌意味着它频繁读不到用户历史，可能输出默认回答或问重复问题，用户体验直线下降。

## 三、连接数突然飙升

- 可能原因：
  1. Agent 实例数瞬时扩缩容：比如突发流量触发 HPA 拉起大量 Pod，每个 Pod 建立连接，但旧 Pod 未正常释放连接（CLOSE_WAIT 堆积），连接数只增不减。
  1. 连接池配置失误：代码里为每次记忆读写新建连接，用完不还。这在 Agent 循环里（特别是 ReAct 模式多次工具调用）会指数级引爆连接数。
  1. 网络抖动导致重连风暴：Redis 短暂不可达，所有 Agent 同时断开并重连，一瞬间成千上万个连接建立。
- 关键排查命令：CLIENT LIST 看来源 IP 分布，如果都是正常 Agent IP 但数量巨大，就是应用侧泄漏；如果出现未知 IP，可能是被扫描或入侵。

## 四、内存碎片率突然飙升

“这个指标很容易被忽视，但它是慢性杀手。”

- 正常范围：1 ~ 1.5。超过 2 就要警惕，超过 5 基本属于事故边缘。
- 可能原因：
  1. 大小不一的记忆频繁增删：Agent 记忆的典型场景——会话开始写入大量临时记忆（tool 输出、推理链），会话结束又批量删除。Redis 的 jemalloc 分配器若无法复用这些大小不一的内存块，就会留下大量空洞。
  1. 频繁修改已存在的 Key 大小：比如对一个 List 不停 LPUSH / LTRIM，或者对一个 String 执行 APPEND 导致内存重分配，旧空间释放后形成碎片。
  1. 开启了 activedefrag 但配置不合理：自动碎片整理没跑起来或跑得太慢，碎片越积越多。
- 危险后果：进程实际占用物理内存（RSS）远大于 used_memory，可能操作系统报 OOM 但 Redis 自己以为还有空间。这会直接导致 Agent 连接被拒或 Redis 被系统 kill。
