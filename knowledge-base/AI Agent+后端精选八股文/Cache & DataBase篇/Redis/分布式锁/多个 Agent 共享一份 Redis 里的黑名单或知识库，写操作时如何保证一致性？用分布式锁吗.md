# 多个 Agent 共享一份 Redis 里的黑名单或知识库，写操作时如何保证一致性？用分布式锁吗？锁超时时间怎么设？

这个场景太典型了，比如多个风控 Agent 同时更新一份 IP 黑名单，或者多个客服 Agent 同时修正同一个知识库条目。不控制的话一定会出现丢失更新，所以我一般分两层来保障：普通操作靠乐观锁 + Lua 原子脚本，强冲突场景才上分布式锁，而且锁超时一定根据数据特点来动态设定，绝不死板。

我按场景从轻到重来说。

## 一、能用原子操作就不用锁

黑名单添加、删除，或者知识库的简单字段更新，很多时候用 Redis 自带的原子命令或 Lua 脚本就能搞定，根本不需要分布锁。

- 添加黑名单：直接用 SADD，Set 结构天然幂等，不存在覆盖问题。
- 更新知识库条目：如果只是修改某个字段，用 Lua 脚本把“读取→修改→写回”包装成一个原子操作，Redis 单线程执行，中间不会插入其他命令。
- 版本控制：更复杂的更新我会给每个知识库条目加一个 version 字段，客户端用 WATCH + MULTI 做乐观锁。如果版本变了就重试，冲突率低时比悲观锁高效很多。

这一层能解决 80% 的并发写场景，代码简单，性能也最高。

## 二、必须用分布式锁时怎么设计

当更新逻辑涉及多个 Key 的非原子操作，或者要跨外部 API 调用，乐观锁就不够用了。这时候我会用分布式锁，但绝不自己造轮子，而是用 Redlock 或者 Redis 的 SET NX PX 实现互斥。

典型设计：

1. 锁的 Key 命名带业务前缀和资源 ID，比如 lock:blacklist:update:20241001，保证锁的粒度尽量细，只锁定受影响的资源范围，不要一把大锁卡住所有 Agent。
1. 加锁命令用 SET lock_key unique_value NX PX timeout_ms，unique_value 是每个 Agent 实例的 UUID，释放时用 Lua 脚本先检查 value 是否匹配再删除，防止误删别人的锁。
1. 获取锁的 Agent 执行写操作，完成后主动释放；如果操作超时未完成，锁自动过期，防止死锁。

## 三、锁超时时间怎么设——核心是看业务容忍度

锁超时设短了业务没执行完锁就释放，导致并发冲突；设长了万一拿到锁的 Agent 挂了，其他 Agent 干等。我一般这样计算：

```
锁超时 = 平均执行时间 × 2 + 网络抖动余量
```

具体分两类数据：

- 黑名单这类短平快操作：写 Redis 的耗时通常在毫秒级，我设 500ms 到 2s 就足够，留出 GC 停顿和网络重试的余量。
- 知识库复杂更新：如果操作需要查外部服务、做数据清洗，那就要根据实际压测的 P99 耗时来设。假设 P99 耗时 800ms，我就设 2s 左右。同时会在业务代码里做好续期：如果操作还在进行中，定时用 Lua 脚本延长锁的 TTL，防止锁提前过期。

## 四、兜底策略：锁超时后的脏数据修复

即使锁超时设计得再合理，极端情况下（比如 Full GC 长时间停顿）仍可能发生锁超时而业务还在执行，导致两个 Agent 同时写。所以我还会加最终一致性检查：

- 用 ZADD 把每次修改操作的时间戳和操作者记录到审计日志里，异步任务扫描同一资源短时间内是否有并发写，如有则标记“需人工复核”。
- 黑名单这种数据允许少量覆盖，但知识库不允许。知识库会存储多个版本，即使并发写产生两个版本，后续 Agent 读取时根据版本号和修改时间协商出最终值。

## 五、监控与告警

锁的争用频率、持锁超时次数、加锁失败次数，这些指标全部接入 Prometheus。如果某个锁的等待队列持续增长，说明锁粒度太粗，需要拆细；如果锁超时频率突增，说明下游服务变慢，需要扩容或降级。

## 写一致性方案决策图（文本）

```
写操作是否涉及多个 Key 或外部调用？
   │
   ├── 否 → 原子命令 / Lua 脚本 / WATCH 乐观锁
   │
   └── 是
         │
         ▼
      是否需要强一致性且冲突概率高？
         ├── 是 → 分布式锁 (SET NX PX + Lua 释放)
         │        ├── 黑名单类 → 锁超时 500ms~2s
         │        └── 知识库类 → 根据 P99 耗时 ×2 + 续期
         └── 否 → 乐观锁 + 异步审计修复
```
