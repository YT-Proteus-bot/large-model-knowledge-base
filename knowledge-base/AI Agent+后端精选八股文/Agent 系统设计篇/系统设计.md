## 题1：设计一个能完成多步骤任务的通用 Agent 系统，核心模块和主循环怎么划分？

**核心判断：**通用 Agent 的模块划分不应按“功能清单”**堆叠，而应按“一次决策循环需要什么**”来切。主循环是骨架，四个支撑模块是器官；模块之间通过显式契约交互，而不是共享一个巨大的上下文。

**主循环**

```
接收任务 → 规划（拆解为子目标）
   → 选择动作（工具/子 Agent/直接回答）
   → 执行动作 → 观察结果
   → 反思（结果是否推进目标？是否需要改计划？）
   → 未完成则回到规划，完成则校验输出 → 交付
```

**四个退出条件必须显式检查，不能只靠模型自评：目标达成、预算耗尽（token/步数/时间）、连续无进展、需要人工介入。**

四个支撑模块

关键设计取舍

规划与执行是否分离？ 建议分离但不僵化：规划产出“可修订的子目标列表”，执行中允许反思触发重规划。纯静态规划在真实任务中很快失效，纯 ReAct 又容易短视。折中是“粗粒度规划 + 细粒度 ReAct”。

反思由谁触发？ 不应每步都反思（成本爆炸），而应在“动作结果与预期不符”“连续两步无进展”“阶段边界”时触发。反思的输入是结构化差异，不是全量历史。

典型失败模式

- 模块间共享可变全局状态：一个模块的写入污染另一个模块的判断。解法是显式状态对象 + 版本号。
- 主循环没有硬终止：模型认为“还可以再试一次”导致无限循环。解法是运行时硬预算，不依赖模型自觉。
- 上下文管理缺位：所有模块都往上下文里写，最终信噪比崩溃。解法是上下文只由上下文管理器统一装配。

面试表达要点：主循环是规划—动作—观察—反思，四个显式退出条件。四个支撑模块各管一件事，通过契约交互而非共享全局状态。核心取舍是“粗规划 + 细执行 + 条件触发反思”，以及“运行时硬预算而非模型自评终止”。

## 题2：设计一个企业知识库问答 Agent，检索、工具调用和答案校验怎么组合？

核心判断：企业知识库问答的失败大头不是“检索不到”，而是“检索到了但答错”和“没检索到却编造”。所以三段式的重心应放在“证据充分性判断”和“答案校验”，而不是把检索 Top-K 调大。

三段式流程

```
意图识别与查询改写
   → 混合检索（语义 + 关键词 + 元数据过滤）
   → 证据充分性判断 ──不足──→ 工具补充（数据库/工单/API）
        │充分                        │
        ↓                            ↓
   基于证据生成答案 ←────────── 回到证据判断
        ↓
   答案校验（引用忠实度 + 事实一致性 + 约束遵守）
        ↓ 不通过
   拒绝 / 标注不确定 / 转人工
```

三个关键设计点

第一，证据充分性判断是分水岭。 不是“有没有检索结果”，而是“检索结果是否覆盖了问题的所有子断言”。实现上可以把问题拆成断言集合，逐个检查是否有证据支撑；缺哪个补哪个，而不是整体重检。

第二，答案校验必须独立于生成。 生成模型倾向于为自己的输出辩护，所以校验应该用独立步骤（规则 + 小模型 + 引用比对），检查三件事：每个断言是否有引用、引用是否真的支持该断言、数字/实体/否定是否与证据一致。引用忠实度是比“答案像不像”更可靠的信号。

第三，拒绝出口是产品能力，不是失败。 知识库没有答案时，明确说“不知道”并给出可操作的下一步（转人工、提交工单），比编造一个看起来合理的答案更可信。拒绝率本身应该被监控——拒绝率突然上升说明知识库覆盖退化。

工具调用的定位

工具不是“检索的替代”，而是“检索的补充”。当知识库只能回答“政策是什么”但不能回答“我的订单是否适用”时，工具负责取实时状态。工具返回应结构化（状态码 + 关键字段 + 引用），而不是原始 JSON。
