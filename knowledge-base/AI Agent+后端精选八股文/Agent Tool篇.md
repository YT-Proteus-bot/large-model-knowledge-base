## 题1：Function Calling 中模型输出的 Tool Call 由谁执行？完整 Tool 调用链路是什么？

**模型只负责“提议调用”，不负责执行。模型输出的是一个结构化的意图表达（工具名 + 参数），真正产生副作用的是模型之外的宿主运行时。这个分工是 Function Calling 安全模型的基础：模型没有直接执行能力，权限校验、幂等控制和错误处理都在运行时手里。**

**完整链路分七段：**

- **① 工具定义注入**——运行时把可用工具的 name、description、parameters schema 放进 tools 字段，而不是拼进自然语言 prompt。
- **② 模型生成 Tool Call**——输出结构化的“工具名 + 参数”，不产生任何副作用，只是一份调用提案。可能一次输出多个，也可能不完整或非法。
- **③ 解析与校验**——先 schema 校验（**字段、类型、枚举**），再语义校验（业务范围），最后权限校验（调用方是否有权调这个工具、访问这些资源）。任何一步失败都不进入执行。
- **④ 策略拦截**——对高风险工具（写操作、支付、外部通信）要求显式确认、二次授权或人工审批。这是模型之外的强制机制。
- **⑤ 实际执行**——调用本地函数、远程 API 或下游服务，负责超时、重试、幂等键、熔断和副作用控制。有副作用的调用必须带客户端生成的幂等键并落盘。
- **⑥ 结果回注**——序列化成模型能消费的 observation，带状态码、关键字段、错误信息和引用指针。
- **⑦ 模型继续推理**——基于 observation 决定继续调用、给答案还是请求澄清，循环到任务完成或触发终止条件。

**一个容易混淆的点：**“选哪个工具”是模型的职责，“是否允许执行”是运行时的职责。合并两者，要么模型被赋予不该有的执行权，要么运行时替模型做了本该由语义判断的选择。

## 题2：Tool 定义中的 name、description、parameters 分别影响模型什么行为？

三者管的是三段不同的行为，对照看更清楚。

> 〔原文此处为飞书内嵌组件，内容未随导出〕

如果只能改一项，优先改 description。它决定“选不选对”，而选错工具的代价通常大于填错参数——填错还能校验重试，选错往往浪费一整轮甚至产生错误副作用。

常见反模式是 name/description 写得极宽、parameters 写得极复杂：模型觉得“这工具什么都能干”，于是频繁误调用；填参时又被一堆字段拖垮。正确方向相反——名字和描述精确到只解决一类问题，参数精简到只留决策必需字段。

## 题3：Tool 库有上百个时，如何做 Tool 路由和动态召回，避免模型选错 Tool？

先诊断问题。工具上百个时，失败很少是“在正确候选里选错了”，更多是三种：该用的工具根本没被召回；召回了一堆语义相近的干扰项；schema 塞满上下文，注意力被稀释。所以解法不是“让模型更聪明”，而是把“全量选择”拆成“分层召回 + 小候选集内选择”。

分层方案：

- 粗召回：按当前任务意图、对话上下文、历史调用模式，从全库召回 20–50 个候选。目标是“不漏”，不是“精确”。
- 精排：综合语义匹配度、当前权限、下游健康度、该工具在此类任务上的历史成功率，排到 Top-5 到 Top-10。
- 只注入 Top-K 的完整 schema；复杂工具可先注入精简 schema，选定后再展开。
- 模型在 Top-K 内选择，并给它一个显式的“无合适工具 / 需要澄清”出口，而不是逼它在错误候选里硬选。
