# 推理优化

> 主题：AI Agent+后端精选八股文 › 大模型基础篇　｜　原始文件：AI Agent+后端精选八股文/大模型基础篇/推理优化.md

## 题1：Prefill 和 Decode 分别是什么瓶颈？为什么不能用一个“平均延迟”指标来评估推理性能？

Prefill 是计算密集型（compute-bound），Decode 是访存密集型（memory-bound）——两者受限于完全不同的硬件资源，没有任何一个标量延迟能同时刻画它们。

Prefill 处理整段输入 prompt，所有 token 的 Q、K、V 可以并行计算，矩阵乘法的算术强度高，瓶颈在 GPU 的算力（FLOPS）。Decode 每步只生成一个 token，需要读取全部历史 K、V 和模型权重，但只产出一行输出，算术强度极低，瓶颈在显存带宽（HBM bandwidth）。一个具体的量级：Prefill 阶段几乎全部延迟可归因于计算，而 Decode 阶段只有不到 20% 的延迟与计算有关，其余都被访存主导。

用“平均延迟”会掩盖两个在工程上完全不同的优化问题。 如果你只看一个端到端的平均 token 耗时，Prefill 的排队延迟和 Decode 的逐 token 生成延迟被混在一起，你无法判断是该增加算力（对 Prefill 有效）、提升显存带宽利用率（对 Decode 有效），还是该改调度策略（比如把 Prefill 和 Decode 分离到不同 GPU）。正确的做法是至少拆成 TTFT（Time To First Token，反映 Prefill + 排队） 和 TPOT/ITL（Time Per Output Token / Inter-Token Latency，反映 Decode 的单步耗时）。把两者混成一个数，等于把“排队等 prefill”和“逐字往外蹦”当成同一件事来优化，优化方向必然是错的。

## 题2：KV Cache 缓存的是 K 和 V 而不是 Q，从自回归解码的计算模式解释为什么？

Q 每一步都是新的，K 和 V 是历史累积的“检索库”，缓存 Q 没有任何复用价值。

直观的类比是：Q 是“这次要问的问题”，每次都不同；K/V 是“已经建好的答案库”，越积越多，缓存问题没有意义，缓存答案库才能避免重复计算。

如果每步都重新计算历史 K、V，第 t 步的注意力计算量是 O(t2)；缓存之后，每步只需计算新 token 的 K、V 并与缓存中的历史 K、V 拼接，单步计算量降到 O(t)，代价是缓存占用随序列长度线性增长。这就是“用显存换计算”的核心权衡。

GQA 下约 17.2 GB，是 MHA 的 25%。如果模型权重本身约 14 GB（7B × 2 bytes），MHA 的 KV Cache 已经是权重的近 5 倍；GQA 把它压到与权重相当的量级。这就是为什么 Llama-2 70B 和后续模型普遍采用 GQA 或 MQA——不是精度上的选择，是显存容量上的硬约束。

## 题4：PagedAttention 借鉴了操作系统的什么思想？它解决的是“显存不够”还是“显存碎片和共享”问题？

借鉴的是虚拟内存分页：把连续的逻辑地址空间映射到不连续的物理页框，通过页表翻译。

PagedAttention 把 KV Cache 切成固定大小的 block（类似 OS 的页），每个请求维护一张 block table（类似页表），按需分配、动态映射，而不是为每个请求预分配一整块最大长度的连续显存。vLLM 论文的原文是：受经典虚拟内存和分页技术启发，实现 KV cache 的近零浪费和跨请求的灵活共享。

它解决的核心问题是碎片和共享，不是“显存不够”这个笼统的说法。 传统预分配方案的有效利用率只有 20–40%，大量显存被“预留但未使用”的尾部空间和外部碎片浪费掉。PagedAttention 把有效利用率提升到接近 100%，同时通过 block 级别的 copy-on-write 支持并行采样和前缀共享。换句话说，它让同样的显存能容纳更多的并发请求和更长的序列，而不是让模型本身变小。如果物理显存真的不够，PagedAttention 也无法凭空创造容量；它的价值是消除管理低效带来的浪费。

## 题5：静态批处理为什么在 Agent 场景下利用率很低？连续批处理（iteration-level scheduling）具体在哪个粒度上调度？

静态批处理把一批请求“捆成同进同出的命运共同体”：GPU 必须等 batch 内最长的序列完成，才能释放 slot 并接纳新请求。 在 Decode 阶段，短请求早早结束，但它的 slot 一直空占着，GPU 陪着长请求“陪跑”，利用率可以低到 30–50%。

Agent 场景把这个缺陷放大到了极致。 Agent 的工具调用是典型的变长请求：一次 search 可能 2 秒返回，一次 execute_code 可能 30 秒，而且请求到达是突发性的（工具返回后瞬间发起下一轮）。静态批处理要么等一批凑齐再跑（排队延迟），要么让短请求陪长请求跑完（slot 浪费）。Agent 的轮次之间还有依赖关系，短工具的结果本可以尽早返回给模型继续推理，却被静态批的“整批同步”卡住。

连续批处理的调度粒度是每一个 decode step（iteration），而不是整批。每个 iteration 结束后，调度器检查：哪些序列已经完成，立即移除并释放其 KV block；队列中是否有新请求，立即插入空闲 slot。换言之，批的成员在每一步都可以变化，而不是在“一轮”开始时固定。这使得 GPU 在 decode 阶段的空转被压缩到最小，吞吐可以是静态批处理的 2–10 倍。

## 题6：连续批处理提升了吞吐，代价是什么？chunked prefill 解决的是什么问题？

连续批处理的首要代价是调度开销和延迟抖动，而不是“吞吐换延迟”这种笼统的表述。 每个 iteration 都要重新调度、更新 page table、重新组装 batch 的元数据，调度器本身成为 CPU 侧的固定开销。更关键的是尾延迟：高并发下，单请求的 ITL（inter-token latency）会因为排队效应而抖动，新请求的插入可能让已经在 decode 的请求在某个 iteration 被延迟。连续批处理让平均吞吐变好，但不保证每个请求的延迟都更优。

chunked prefill 解决的是另一个正交问题：长 prefill 对 decode 的阻塞。 连续批处理允许新请求在每个 decode step 插入，但如果一个请求的 prefill 很长（比如 32K token 的 prompt），它会在一整轮里独占计算资源，已经在 decode 的请求被迫等待，p99 ITL 出现尖峰。chunked prefill 把长 prompt 的 prefill 切成小块（典型 512–8192 token），在每个 iteration 的 token 预算内与 decode 请求交错执行：先处理一小块 prefill，再处理一些 decode，再处理下一块 prefill。代价是 TTFT 略微上升（分块带来额外开销，且长 prompt 的 prefill 被拉长到多个 iteration），换来的是 ITL 的大幅改善和整体吞吐的提升（基准中 ITL 提升约 50%）。一句话：连续批处理管“批的成员怎么变”，chunked prefill 管“一个长 prefill 在一轮里占多少”，两者组合才能同时控制吞吐和尾延迟。
