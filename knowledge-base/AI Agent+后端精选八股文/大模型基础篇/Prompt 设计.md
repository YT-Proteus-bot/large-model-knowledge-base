# Prompt 设计

> 主题：AI Agent+后端精选八股文 › 大模型基础篇　｜　原始文件：AI Agent+后端精选八股文/大模型基础篇/Prompt 设计.md

## 题1：Agent 的系统 Prompt 应包含哪些固定模块？哪些内容不该放进系统 Prompt？

一个有效的系统 Prompt 应包含五个核心模块，按固定顺序组装：身份与目的 → 行为规则 → 响应格式 → 边界情况处理 → 示例。

身份与目的（Identity & Purpose） 定义 Agent 是谁、为谁服务、完成什么任务。行为规则（Behavioral Rules） 定义它能做什么、不能做什么——最常被忽略的是“不能做什么”。一个只知道“自己是什么”但不知道“自己不能做什么”的 Agent，会朝意想不到的方向即兴发挥。

响应格式（Response Format） 规定输出的结构、长度、语言和格式约束。边界情况处理（Edge Case Handling） 覆盖工具返回空结果、参数缺失、下游故障、信息不足等场景的应对策略。示例（Examples） 用 few-shot 校准模型行为，比纯指令更有效。

组装顺序的原则是：稳定内容放前面，变化内容放后面。 Rasa Mantle 的系统 Prompt 组装顺序是：persona 和 rules → skills → channel rules → 日期时间 → project memory → 当前激活的 skill 或路由内容。这样做的目的是让稳定文本成为公共前缀，使 prompt-prefix cache 在轮次之间保持命中。

不该放进系统 Prompt 的内容：

- 工具清单和参数细节。模型已经从 tools 参数中看到了所有工具定义，在系统 Prompt 中重抄只会造成两边不同步。
- 与当前任务无关的大量业务规则。把所有场景的退款规则、代码规范、格式要求塞进一个 Prompt，大部分 token 与当前任务无关，会稀释注意力。
- 本应由代码补全的字段（如 ticket_id、idempotency_key）。模型能填的字段越少，它出错的面就越小。
- 检索片段或工具返回的原始内容。这些是动态的、不可信的数据，应该通过独立的上下文通道注入，而不是固化在系统 Prompt 中。

## 题2：系统 Prompt、工具 Schema、检索片段、历史记忆在上下文中的占比如何建模和定位最大项？

上下文窗口的可用空间不是“模型宣称的最大 token 减去消息 token”这么简单。必须预留输出空间、安全裕量，并对输入占用做显式建模。

一个可操作的公式是：

```
可用输入 = 模型窗口 - 输出预留 - 安全裕量
输入占用 = 系统提示 + 工具定义 + 历史消息 + 当前输入 + 记忆附件 + 检索片段
```

最大项通常是历史消息，而不是系统 Prompt 或工具 Schema。 一个具体的量级参考：50 次工具调用、每次结果 2K tokens，会给后续每一次请求增加 100K tokens 的历史负担。工具 Schema 的问题在工具数量膨胀时才会凸显——28 个工具的 Schema 可以耗尽 8K 上下文窗口，在 16K 窗口下只剩 6–11 个检索块的余量。

工程上必须做的两件事：第一，上下文诊断可视化——展示各来源的 token 占比（系统提示、工具 Schema、消息、记忆、检索、压缩后保留段），而不是只显示总数，否则用户无法理解“为什么刚开始对话就很满”。第二，分级压缩策略：延迟工具加载 → 截断单个结果 → 替换历史大结果 → 微压缩冗余块 → 生成整体摘要，从低信息损失到高信息损失逐级使用。

## 题3：工具调用场景下，Prompt 如何约束模型“先选工具再回答”，而不是直接编造结果？

核心指令是“tool-first, not tool-only”，并且这条规则必须写成硬约束，而不是建议。

一个经过验证的 Prompt 表述是：

Be tool-first, not tool-only. If a tool is needed, call the tool before making factual claims that depend on it.

这条规则的关键在于“依赖工具的事实性断言”这个限定。它不是要求模型对所有问题都先调工具，而是要求：当一个事实性结论需要工具结果才能成立时，调工具必须发生在做出该断言之前。与之配套的 grounding 规则是：“任何具体的数值结果都必须可追溯到工具结果或用户明确提供的数字。如果工具不支持精确场景，不要编造估算。”

Prompt 还需要覆盖失败和空结果场景，否则模型在工具没有返回有用数据时更容易编造。可行的约束包括：“如果工具返回空结果、零结果、失败或校验错误，不要假装任务成功”“当工具结果不完整时，给出部分答案并简要解释限制”。

Prompt 不是唯一的强制手段。 对于“必须先调某个工具”的场景，可以使用 API 层的 tool_choice 强制第一个调用必须是指定工具。Prompt 管的是“模型的理解和默认倾向”，API 约束管的是“硬性的执行顺序”，两者配合才能可靠地阻止编造。

## 题4：工具 description 和系统 Prompt 中的工具使用说明如何分工？写重复了会有什么问题？

分工原则：description 管“这一个工具”，系统 Prompt 管“跨工具的策略”。 工具描述是写给模型看的 Prompt，但它的作用域是单个工具；系统 Prompt 中不应该重抄工具清单或参数细节。

工具 description 应覆盖五个部分（Vercel 的 5-section contract）：WHEN TO USE（何时使用，用用户会说的语言，而不是数据库 schema 名）、WHEN NOT TO USE（何时不用，软引导，“prefer X”）、DO NOT USE FOR（硬边界，“never use this for Y”）、USAGE（参数约束和默认值，模型无法从 schema 推断的那些）、EXAMPLES（2–3 个具体调用示例）。

重复或冲突带来的问题：

第一，浪费 token 并稀释注意力。 同一段策略模板在每个工具的 description 后重复拼接，read-only 工具多 443 字符，side-effecting 工具还要更多，而且每次请求都对每个 MCP 工具重复发送一遍。工具定义排在缓存前缀的最前面，description 的每一句冗余都在增加首次写入和缓存未命中时的固定成本。

第二，两边不同步导致行为不一致。 系统 Prompt 中写了一套工具使用规则，description 中写了另一套，模型会收到矛盾的信号。更严重的是，改了工具实现却忘了改 description，模型会按照旧描述使用工具，结果对不上。

第三，相似工具的 description 如果“各写各的、不互相点名”，模型无法区分。 两个 search 工具都写“搜索相关内容”，模型只能猜。正确的做法是在双方 description 中沿同一条对立轴划界，并互相点名：“搜索文件内容（不要用于读取已知文件，读取请用 read）”和“读取已知文件（不要用于搜索模式，搜索请用 grep）”。

## 题5：多工具场景下，如何通过 Prompt 降低近义工具误选和轮次分布右移？

近义工具误选的根因是注意力稀释：工具越多，模型分到每个工具上的注意力越少。实测数据：5 个工具时选择准确率约 85%，15 个时约 65%，30 个时约 45%（几乎随机）。轮次分布右移的本质是模型在反复试探和纠正——选错一次，看到错误结果，再选一次，多消耗了轮次。

可操作的策略：

策略一：工具分层分类。 把扁平的 20 个工具列表改成按语义分组的层级结构（知识检索类、数据查询类、写操作类），每组内工具数量少、边界清晰，模型的选择空间被压缩。

策略二：description 用“对立轴”划界并互相点名。 相似工具不能各自写一句模糊的“搜索相关内容”，而要在描述中明确“我做什么、不做什么、替代品是谁”。5-section contract 中 WHEN NOT TO USE 和 DO NOT USE FOR 的双重否定是刻意设计的——模型在描述薄弱时会“泄漏”回最通用的那个工具（bash gravity），说一次“不要用”不够，说两次几乎总是够。

策略三：动态工具剪枝/懒加载。 不要把全部工具 Schema 一次性塞进上下文。根据当前任务阶段只暴露最小必要集合（通常 3–5 个），工具描述短、选择就锐利。Tool Attention 机制可以将每轮工具 token 减少 95%（47.3K → 2.4K），上下文利用率从 24% 提升到 91%。

策略四：选择后验证。 在程序层面校验工具选择的合理性（参数是否在枚举范围内、目标工具是否与意图匹配），发现明显错误时不执行，而是把错误信息作为 tool_result 返回给模型，让它下一轮自己修正。错误消息本身是“事后的 description”——写“date 需要 YYYY-MM-DD，你给的是 'June 5'”比回一个 opaque 的 error code 更能让模型自我纠正。
