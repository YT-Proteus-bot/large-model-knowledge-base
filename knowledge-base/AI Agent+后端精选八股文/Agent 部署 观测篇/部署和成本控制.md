## 题1：Agent 服务如何部署？高并发下为什么要用无状态 Runtime + 消息队列，而不是同步 HTTP 直接扛？

**核心判断：**同步 HTTP 的问题不是“慢”，而是它把“连接的生命周期”和“任务的生命周期”绑死了。 Agent 任务天然是慢的、I/O 密集的、非确定的、按 token 计费的。一个任务可能跑 90 秒甚至几分钟，同步 HTTP 在这段时间里一直占着连接和线程，标签页一关任务就丢了，网络抖动时它可能重试一个已经计费的操作，任务失败时前面 96 秒的计算全部白费，而且它无法被取消。压力测试的实测数据很直白：500 并发下，同步 HTTP 的错误率是 50%，响应时间是 30 秒——完全不能用。这不是“调优能解决”的问题，是架构假设错了。

**无状态 Runtime + 消息队列的做法**，是把“提交”和“执行”解耦。 **接入层只做三件事：**鉴权、校验、把任务写入队列，然后立刻返回一个 task_id。Worker 从队列领取任务执行，执行状态持久化到外部存储，前端通过查询接口或 SSE 流式接口获取进度。这样连接可以断、可以重连，任务不会丢；Worker 可以水平扩缩，因为它不持有会话状态；重试和取消变成了队列层面的能力，而不是“再发一次 HTTP 请求”。

消息队列在这里承担的不只是“削峰”，**而是四个确定性语义：** 任务持久化（**入队即落盘，进程崩了任务还在**）、重试与死信（失败任务进入 DLQ，而不是静默消失）、背压（队列深度是扩缩容的信号，而不是让请求直接打到模型）、幂等键的载体（同一个 task_id 的重复投递可以被去重）。Protobuf 比 JSON 体积小 30–50%，序列化快 3–10 倍，适合作为 Agent 间消息的编码格式。

**面试表达要点：**同步 HTTP 把连接生命周期绑死在任务生命周期上，在 Agent 这种慢、I/O 密集、按 token 计费的工作负载下，错误率和延迟会随并发线性恶化。无状态 Runtime + 消息队列把提交和执行解耦，换来的是可持久化、可重试、可扩缩、可取消——这是 Agent 后端和普通 Web 后端最根本的区别之一。

## 题2：Agent 部署时如何设计弹性扩缩容？按 QPS、排队长度还是 Token 消耗扩缩容更合理？

**核心判断：**QPS 是最差的单一扩缩容信号，因为它假设“每个请求的成本相近”，而 Agent 的工作负载恰恰不是。 一个简单的问答和一个多步工具调用链的 QPS 可能一样，但后者消耗的 token、工具调用次数和耗时可能是前者的几十倍。按 QPS 扩容，会在轻任务涌入时过度扩容，在重任务堆积时扩容不足。

合理的扩缩容是“按资源池分层 + 按队列需求信号”的组合。 Agent 平台应该按接入/编排器、CPU Worker、GPU 推理、外部工具调用池分别扩缩容，而不是用一个平均指标掩盖局部瓶颈。

Token 消耗是扩缩容的“关联信号”，而不是主信号。 它适合用来做容量规划和成本预测，但直接按 token 消耗来扩缩容会有滞后——token 是消耗出来的，不是排队中的。队列深度和最老任务年龄是更前置的信号：它们反映的是“有多少工作已经在等”，而不是“已经花了多少钱”。

扩容必须受下游约束。 如果下游模型的 RPM/TPM 或数据库连接数已经满了，增加 Worker 只会扩大 429 和重试风暴。缩容也不是简单杀进程：应该先停止领取新任务，让运行中的步骤到 Checkpoint 后排空，再释放租约；有副作用的调用不能强杀。

面试表达要点：不要用 QPS 一刀切。接入层按 QPS，Worker 按队列年龄和服务时间，GPU 池按 token 吞吐和显存，工具池按下游 429 和配额。Token 消耗适合容量规划，不适合做主扩缩容信号。扩容受下游 RPM/TPM 约束，缩容要优雅排空。

## 题3：Agent 的 SSE 流式输出如何部署，才能避免长连接占满线程池和连接数？

核心判断：SSE 长连接占满线程池的根因不是“连接多”，而是“一连接一线程”的部署模型。 在传统 Servlet 或同步 Web 框架下，每个 SSE 连接会长时间占住一个工作线程，工作线程数就是并发连接数的硬上限。一万个并发 SSE 连接，如果每个都占一个线程，就需要一万个线程——这在任何 JVM 或 Python 运行时里都不可持续。

解法是事件驱动非阻塞 I/O，让长连接“占状态”而不是“占线程”。 使用 Netty、WebFlux、Node.js 或 Go 协程，读取模型流后由事件循环写入 SSE，禁止请求线程阻塞等待。模型 SDK 和 HTTP 客户端应该异步化，或者使用隔离的有界线程池；阻塞依赖不能污染公共事件循环。

连接数本身的优化同样重要。 传统 SSE 是单会话单连接，60% 的连接处于闲置等待状态，万级并发需要万级 TCP 连接，CPU/内存占用超过 70%。SSE 长连接复用通过会话绑定、多路复用和连接池管理，让单连接承载多会话（N:1，N≤5），实测并发连接数降低 60%，资源占用下降 45%。基于 HTTP/2 的多路复用可以让单 TCP 连接承载多个会话流，通过 Session-ID 区分数据。

慢消费者是另一个隐性杀手。 每个连接应该维护有界发送队列和最大待发字节；慢消费者达到阈值时，合并 chunk、暂停上游、降采样或断开，避免内存累积。心跳由共享时间轮批量驱动，设置空闲超时和最大连接时长，客户端断开时取消信号要向模型和工具传播，及时释放 token 预算。

面试表达要点：SSE 占满线程池的根因是“一连接一线程”，解法是事件驱动非阻塞 I/O，让长连接占状态不占线程。同时用长连接复用（N:1）降低连接数，用有界发送队列和慢消费者保护防止内存膨胀。网关层要关缓冲、用 HTTP/2、不做响应压缩。

## 题4：多租户 Agent 部署如何做计算、数据和模型隔离？隔离级别如何影响部署成本？

核心判断：隔离级别不是一个“要不要隔离”的二值选择，而是一条从“完全共享”到“完全独立”的频谱，每一档都在隔离强度、资源效率和成本之间做不同的取舍。 AWS 的框架把部署模型分为“孤立（siloed）”和“池化（pooled）”：计算和依赖资源可以按租户独占，也可以跨租户共享。Azure 的逻辑多租户在共享资源中通过租户专属分区或索引来隔离数据，物理多租户则为每个租户提供独立的基础设施。

计算隔离的三个档位：

共享 Agent + 上下文隔离（逻辑隔离） ：所有租户共用同一组 Agent 实例，通过访问控制和租户上下文区分数据。隔离强度是逻辑级的，资源效率最高，适合标准客户和通用 Agent。

池化但按租户分区：共享计算资源，但数据层按租户分区（如 Cosmos DB 分区键、Redis 命名空间前缀）。隔离强度介于逻辑和物理之间，资源效率较高。

完全独立（物理隔离） ：每个租户有独立的 Agent 实例、独立的存储和独立的模型部署。隔离强度最高，但资源效率最低，空闲浪费严重，成本随租户数线性增长。

数据隔离通常比计算隔离更容易做到“逻辑上充分”。 共享数据库 + 租户分区键 + 行级访问控制，在很多场景下已经足够，不需要为每个租户开独立数据库。真正的物理数据隔离只在合规强要求（如金融、医疗）或租户明确付费购买时才值得。

模型隔离是最贵的一档。 共享模型端点 + 租户级配额和限流是默认选择；为每个租户部署独立模型实例意味着 GPU 闲置成本无法摊薄。只有在模型微调需要租户专属权重、或者数据驻留要求禁止跨租户共享推理路径时，才值得做模型级物理隔离。

隔离级别对成本的影响是结构性的，不是线性的。 逻辑隔离的成本随租户数缓慢增长，物理隔离的成本随租户数线性增长。混合策略（标准客户池化、高价值客户独立）通常是最优的——用池化摊薄大部分租户的成本，用独立实例为少数租户提供强隔离。

面试表达要点：隔离是一条频谱，不是二选一。计算通常逻辑隔离足够，数据用租户分区键，模型默认共享端点 + 租户配额。物理隔离的成本随租户数线性增长，只在合规或高价值客户场景使用。混合策略——池化为主、独立为辅——通常是最优的成本/隔离平衡。
