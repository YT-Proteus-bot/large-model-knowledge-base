## 题1：相比单体应用，多 Agent 系统的可观测性要怎么设计？Logs、Metrics、Traces 上分别需要增加哪些多 Agent 独有的信号？

**核心判断：**单体观测回答“一条链路走没走通”，多 Agent 要回答“任务树怎么被拆分、分派、执行、聚合，哪条边出了问题”。 观测对象从调用栈变成“任务树 + 边 + 消息”，三者必须通过同一套 ID 关联。

**Logs：**补四类。 路由决策（**候选集、分数、排除理由、置信度**）、委派与消息（handoff_id、message_id、发送/接收时间、payload 哈希）、共享状态读写（谁、何时、基于哪个版本、覆盖还是合并）、Agent 版本（agent_id + agent_version）。

**Metrics：**按切片补。 按角色（Planner/Worker/Aggregator 各自的成功率、成本、重试率）、按边（每条 from→to 的 handoff 成功率、传递错误率）、按拓扑（fan-out/fan-in 规模、委派深度）、按失效模式（**路由漂移率、停滞率、互踢率、降级率**）。

**Traces：**补多种边类型。 Span 带 agent_id、handoff_id、routing_decision、context_version；父子 Span 只表达时间包含，消息因果用 message_id + Link，委派用 delegates 边，fan-in 用 Span Links。任务树是一等公民，不能平铺成一条链。

面试表达要点：不是“多个单 Agent 加日志”，而是把观测对象升级为任务树。Logs 补决策和传递，Metrics 补按角色/边/拓扑的切片，Traces 补多 Agent ID 和多种边类型，三支柱靠同一套 ID 串起来。

## 题2：多 Agent 链路追踪中，单纯用父子 Span 为什么不够？调用因果、消息因果和委派关系分别应该怎么表达？

核心判断：父子 Span 表达的是“时间包含关系”——子 Span 在父 Span 的时间窗口内执行。但多 Agent 系统里有三种因果关系并不满足“时间包含”：异步消息、fire-and-forget 委派、以及多输入聚合。 用父子关系硬套这三种因果，会把“A 发消息给 B，B 稍后处理”画成“B 是 A 的子节点”，把“C 聚合了 A、B 的结果”画成“C 是 A、B 的父节点”——这会让排障时误判“谁在等谁”。

三种因果的表达方式：

调用因果（A 调用 B，B 返回结果给 A） ——可以用父子 Span，但要额外记录 call_type（sync/async）和 result_consumed_by。同步调用中 B 的 Span 在 A 的时间窗口内，父子关系成立；异步调用中 B 可能在 A 结束之后才执行，父子关系不成立，应该用 Span Links 表达“B 是由 A 触发的”，而不是“B 是 A 的子节点”。

消息因果（A 发消息给 B，B 稍后消费） ——不能用父子 Span。应该用 message_id / correlation_id 把发送事件和消费事件关联起来，两边各自是独立的 Span，通过 Link 连接。关键属性包括：sent_at、received_at、queue_wait_ms、payload_hash。消息因果的核心是“时间上不连续，但数据上连续”。

委派关系（A 把任务委派给 B） ——需要区分三种委派语义：同步委派（A 等 B 完成）、异步委派（A 不等 B，B 独立执行）、转移委派（A 把任务所有权交给 B，A 不再参与）。三者在 Trace 上的表达不同：同步委派可以用父子 Span + delegation_type=sync；异步委派用 Span Links + delegation_type=async；转移委派需要记录 ownership_transferred_to，并且 A 的 Span 应该标记 terminal_state=delegated，而不是 success。

一个可操作的设计：用“边类型”而不是“父子关系”来建模。 任务树上可以有四种边：contains（时间包含）、triggers（调用触发）、messages（消息传递）、delegates（委派）。父子 Span 只表达 contains，其余三种用 Link 或显式的边记录表达。这样排障时能看到“B 是被 A 触发的，但不在 A 的时间窗口内”，而不是误以为“B 是 A 的子步骤”。

面试表达要点：父子 Span 只表达时间包含，无法表达异步消息、fire-and-forget 委派和多输入聚合。调用因果用父子 + call_type，消息因果用 message_id + Link，委派关系用 handoff_id + delegation_type。正确做法是用“边类型”建模，而不是把所有关系都压成父子。

## 题3：一个端到端失败涉及路由、规划、检索、工具、子 Agent 输出和聚合，你按什么顺序定位“第一个偏离点”，而不是追最后的报错节点？

核心判断：不要从报错节点往回追，要从聚合节点往下找“第一个契约违反点”。 报错节点只是错误的暴露点，不是产生点。多 Agent 的失败会沿任务树向上传播并在聚合层放大，最后报错的往往是“承接了上游错误前提”的聚合步骤。

排查顺序：

第一步，从聚合节点开始，检查它的输入。 聚合节点的职责是“把多个子 Agent 的输出合成最终结果”。先看：它收到的输入是否符合各子 Agent 的输出契约？如果某个子 Agent 的输出在聚合节点看来是“缺失字段/格式错误/语义矛盾”，偏离可能发生在传递层或子 Agent 执行层。

第二步，逐个检查子 Agent 的产出是否符合它自己的契约。 对每个子 Agent，看它的输出是否满足“输入契约 → 输出契约”的映射。如果输入正确但输出错误，偏离在这个子 Agent 内部；如果输入本身已被污染，偏离在上游。

第三步，检查路由和规划。 如果所有子 Agent 的执行都“符合契约”，但最终结果错了，问题可能在拆分（子任务集合不能覆盖原任务）或分派（子任务分给了不合适的 Worker）。看任务树的结构：子任务之间是否有重叠、是否有遗漏、路由决策是否合理。

第四步，检查检索和工具。 如果某个子 Agent 的输入正确但输出错误，下钻到它的步骤：检索是否召回了关键证据、工具返回是否符合预期、模型是否基于错误上下文做了推理。

“第一个偏离点”的判据：

找到第一个“输入符合契约、输出违反契约”的节点；如果所有节点都符合契约，找到第一个“输入已经被污染”的节点。

为什么不能追最后报错节点： 最后的报错可能只是“聚合节点发现输入矛盾”，但矛盾是上游两个子 Agent 各自“正确执行”后产生的。修聚合节点只能掩盖症状，下一次同样的上游矛盾会以另一种形式暴露。

面试表达要点：从聚合节点往下找，先看聚合输入是否符合子 Agent 契约，再看每个子 Agent 的输入输出是否匹配，最后看路由和规划。第一个偏离点是“输入对、输出错”的节点，或“输入已被污染”的节点。追最后报错节点只能修暴露点，不能修产生点。

## 题4：多 Agent 失败可以拆成“拆分错、分派错、执行错、传递错”，Trace 上如何区分这四类责任？

核心判断：四类失败对应任务树上的四个不同位置——拆分错在“树的形状”，分派错在“边的选择”，执行错在“节点内部”，传递错在“边的传输”。 区分它们的关键不是看“哪里报错”，而是看“契约在哪个环节被违反”。

区分“执行错”和“传递错”的关键证据：

在子 Agent 产出时记录一个 output snapshot（output_hash、output_size、output_schema），在聚合节点接收时记录一个 received snapshot（received_hash、received_size、received_schema）。如果两者不一致，就是传递错；如果一致但内容不符合契约，就是执行错。

区分“拆分错”和“分派错”的关键证据：

拆分错是“子任务本身就不对”，分派错是“子任务对，但给错了人”。看任务树的子任务契约：如果子任务契约的并集不能覆盖原任务，是拆分错；如果子任务契约正确但 routing_decision 显示选了一个能力不匹配的 Worker，是分派错。
