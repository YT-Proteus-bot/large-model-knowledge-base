# Agent 核心概念

> 主题：AI Agent+后端精选八股文 › Agent 基础篇　｜　原始文件：AI Agent+后端精选八股文/Agent 基础篇/Agent 核心概念.md

## 题1：什么是 AI Agent？它和“带工具调用的 LLM 应用”本质区别在哪？

本质区别是控制流的归属：工具调用应用的控制流是开发者预定义的，LLM 只负责在固定节点填充参数；Agent 的控制流是模型在运行时根据观察动态决定的，包括“下一步做什么、用哪个工具、要不要继续、什么时候停”。

一个“带工具调用的 LLM 应用”典型形态是：开发者写死流程——先查订单，再判断状态，再调退款接口，最后发通知。LLM 的作用是在“判断状态”这一步做语义分类，或者在“调退款接口”时从用户话里抽取金额和订单号。步骤是固定的，工具选择是固定的，错误处理是枚举好的。 模型不决定“要不要查订单”，也不决定“退款失败后是重试还是换一个工具”。

Agent 的形态是：给定目标和工具集，模型在每一轮自己决定“我现在知道什么、还缺什么、下一步该调用哪个工具、传什么参数”。它可能第一轮查订单，发现订单已发货，第二轮决定查物流而不是退款，第三轮发现物流异常，决定创建工单而不是继续退款。步骤数不确定，工具选择不确定，终止条件由模型判断（或由外部约束兜底）。

这个区别的工程后果是：

- 工具调用应用的测试是“给定输入，验证固定路径的输出”；Agent 的测试是“给定目标，验证它在不同观察下能收敛到正确结果，且不会死循环、不会越权”。
- 工具调用应用的错误处理是“枚举每个节点的失败分支”；Agent 的错误处理是“给模型可操作的反馈，让它自己调整，同时用最大步数、预算、审批闸门兜底”。
- 工具调用应用的“规划”是开发者的流程图；Agent 的“规划”是模型在运行时生成的、可能被后续观察推翻的临时计划。

一句话：工具调用应用是“LLM 嵌在流程里”，Agent 是“流程由 LLM 在运行时生成”。前者可控但僵硬，后者灵活但需要额外的约束机制（步数上限、工具白名单、审批闸门、预算）来防止失控。

## 题2：Agent 的核心组成通常包括哪几部分？规划、工具、记忆、执行循环分别承担什么职责？

四部分：规划（决定做什么）、工具（能做什么）、记忆（知道什么）、执行循环（把三者串起来，并根据观察更新）。四者不是并列的模块，而是循环里的四个角色——规划产生意图，工具产生行动，记忆提供上下文，执行循环决定“下一步”。

- 规划：把目标拆成可执行的步骤，排序依赖关系，并在执行中根据观察调整。它回答“先做什么、后做什么、什么可以并行、失败了怎么办”。规划不是一次性生成完整计划就结束——在 ReAct 类 Agent 中，规划是每一步都重新发生的（“基于当前观察，下一步做什么”）；在 Plan-and-Execute 中，规划是先生成计划、执行中再重新规划。规划的质量决定 Agent 是“有策略地探索”还是“随机试错”。
- 工具：Agent 与外部世界交互的接口，包括查询类（搜索、读库）、写入类（发消息、改状态）、计算类（代码执行）。工具定义要包含：名称、描述（模型据此决定何时用）、参数 schema（模型据此生成参数）、副作用等级（只读/可逆写/不可逆写）、权限要求。工具不是越多越好——工具过多会让模型选择困难、增加误用风险；工具描述不清晰会让模型在错误的场景调用它。
- 记忆：短期记忆是当前会话的上下文（对话历史、中间结果、当前计划状态），存在上下文窗口或会话存储中；长期记忆是跨会话的偏好、事实、经验，存在外部存储（向量库、图谱、结构化表），按需检索注入。记忆的职责不是“记住一切”，而是“在正确的时机提供正确的上下文”——短期记忆维持连贯性，长期记忆提供跨会话的个性化 and 知识。
- 执行循环：把规划、工具、记忆串起来的控制流。典型循环是：观察当前状态（用户输入 + 工具结果 + 记忆检索）→ 规划下一步（模型推理）→ 选择并调用工具 → 观察结果 → 更新记忆/计划 → 判断是否终止。循环的终止条件可以是“模型认为目标达成”“达到最大步数”“预算耗尽”“触发审批闸门”“检测到循环”。执行循环是 Agent 的“操作系统”，它决定什么时候让模型决策、什么时候强制中断、什么时候把控制权交给人。

## 题3：Agent 和 Workflow 的区别是什么？什么场景该用固定工作流，什么场景才需要 Agent？

区别在“路径是否在运行时确定”。Workflow 的路径是开发者预定义的（包括分支、循环、错误处理），LLM 只在固定节点做语义判断；Agent 的路径是模型在运行时根据观察动态生成的。判据是：如果任务的步骤数、工具选择、失败处理可以事先枚举，用 Workflow；如果步骤数不确定、需要根据中间结果动态调整、工具选择依赖语义判断，才需要 Agent。

该用固定工作流的场景：

- 步骤确定且顺序稳定（如“查订单→判断状态→退款→通知”），分支有限且可枚举。
- 错误处理可以逐节点枚举（超时重试、失败告警、人工兜底），不需要模型“临场发挥”。
- 合规/审计要求每一步可预测、可复现，Agent 的运行时不确定性反而是负担。
- 成本敏感：Workflow 的 LLM 调用次数固定，Agent 的调用次数随任务复杂度浮动，可能高一个数量级。

才需要 Agent 的场景：

- 任务步骤数不确定：用户说“帮我处理这个客户的问题”，可能需要查订单、查物流、查历史工单、发补偿、升级人工，步骤数取决于中间发现。
- 工具选择依赖语义判断：同样一个“查”的动作，模型需要根据上下文决定查订单库、查 CRM 还是查知识库。
- 失败后需要重新规划：退款失败可能是因为订单已发货，此时正确的动作不是重试退款，而是查物流并创建工单——这种“根据失败原因切换策略”很难用固定分支穷举。
- 探索性任务：研究、诊断、多源信息整合，路径本身需要根据发现调整。

混合模式是常态：外层用 Workflow 编排确定性步骤（身份校验、权限检查、审批闸门），内层在“需要动态决策”的节点嵌入 Agent 循环。不要为了“用 Agent”而把本来可以枚举的流程交给模型自由发挥——那会增加成本、延迟和不可预测性，换来的灵活性在固定流程里没有价值。

## 题4：ReAct 范式的核心思想是什么？“推理—行动—观察”循环如何驱动工具调用？

核心思想是“让推理和行动交织”：模型在每一步先显式输出推理（Thought，我当前知道什么、还缺什么、下一步该做什么），再选择行动（Action，调用哪个工具、传什么参数），然后观察结果（Observation），基于观察进入下一轮推理。它不是“先规划完再执行”，而是“每一步都重新推理”。

循环的具体形态：

1. Thought：模型基于当前上下文（用户目标、历史观察、记忆）输出一段推理——“用户要查订单状态，我需要先拿到订单号；用户没有提供订单号，但提到了手机号，我可以先用手机号查订单。”
1. Action：模型选择一个工具并生成参数——“调用 search_order_by_phone(phone="138...")”。
1. Observation：工具返回结果——“找到订单 #12345，状态为已发货。”
1. 下一轮 Thought：模型基于新观察重新推理——“订单已发货，用户问的是退货，我需要查退货政策，而不是查物流。”
1. 循环终止：模型输出最终答案（“您的订单已发货，退货政策是……”），或触发最大步数/预算/审批闸门。

ReAct 驱动工具调用的关键机制：

- 推理显式化：Thought 不是装饰，它是模型“选择工具”的依据。没有 Thought，模型可能在不该调用工具时调用、在该调用时跳过。显式推理让工具选择有据可查，也便于调试（“为什么它调了错误的工具”——看 Thought 就知道）。
- 观察驱动下一步：每一轮的 Observation 都会改变模型的下一步决策。如果第一轮查订单失败（“未找到”），模型在下一轮 Thought 里应该调整策略（换查询条件、问用户要订单号），而不是重复同一个调用。
- 循环需要边界：ReAct 天然可能陷入“反复调用同一工具”“在两个工具间 ping-pong”“步数爆炸”。必须有最大步数、重复调用检测、预算上限、审批闸门作为硬约束。ReAct 的灵活性来自“每一步重新推理”，它的风险也来自“每一步都可能跑偏”。

## 题5：Plan-and-Execute 和 ReAct 有什么区别？各自适合什么任务？

ReAct 是“每一步都重新规划”，Plan-and-Execute 是“先规划完整步骤列表，再逐步执行，执行中按需重新规划”。前者短视但灵活，后者有全局视野但规划可能过时。
