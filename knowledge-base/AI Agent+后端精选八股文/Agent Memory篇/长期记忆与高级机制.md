# 长期记忆与高级机制

> 主题：AI Agent+后端精选八股文 › Agent Memory篇　｜　原始文件：AI Agent+后端精选八股文/Agent Memory篇/长期记忆与高级机制.md

## 题1：短期、工作、长期记忆混存同一向量库，检索时怎么保证不会把“当前任务约束”当成“历史偏好”召回？

混存本身不是问题，问题是缺少“类型、权威、时效、作用域”元数据和检索过滤。 不能靠向量相似度自己分辨“这是当前约束还是历史偏好”。

工程上要同时做四件事：

- 分区/命名空间：短期流水、工作记忆、长期偏好、事实、情景记忆分开命名空间或至少带 memory_type 字段；检索时按类型过滤，偏好区不召回约束区。
- 结构化元数据：每条带 authority（当前约束/历史参考）、status（生效/过期/被覆盖）、timestamp、valid_until、tenant_id、session_id、source；检索先过滤再召回，不靠语义猜。
- 当前约束不依赖向量召回：当前任务目标、硬约束、验收条件放工作记忆结构化字段，每轮常驻注入；不放进长期库让检索“碰运气”。长期库只存稳定偏好/事实，且标注“历史参考，非当前指令”。
- 注入分区与冲突裁决：当前约束区在前、历史偏好区在后并标注“非当前事实”；冲突时以当前约束为准，记录冲突。检索 query 带任务/会话作用域，避免跨任务召回。

收束：防止“约束当偏好召回”，靠“类型分区 + 权威/时效/作用域元数据 + 当前约束结构化常驻 + 注入分区和冲突裁决”；向量相似只做候选，不能决定权威。

## 题2：长期记忆写入由模型自主判断，什么信号说明它已经在写入错误事实？写入污染和检索污染怎么分开定位？

错误写入的信号：内容与来源不符、无来源/不可追溯、与当前工具结果冲突、重复/近重复写入率高、写入后很快被覆盖或撤销、大量推测性语言、临时情绪/一次性事件被当稳定事实、跨租户/越权写入、后续检索频繁被人工纠正。

可观测信号包括：写入频率异常、同事实多版本快速更替、写入条目低置信、来源缺失、写入后未被使用、badcase 中“记忆内容本身错”。

写入污染 vs 检索污染，看“存储里有没有错”：

- 写入污染：存储条目本身错——来源不支持、事实错、过时未失效、归属错、重复冲突未合并。定位看写入证据、来源、版本、抽取文本。
- 检索污染：存储条目正确，但被错误召回/注入——query 不相关、过期未过滤、跨租户、排序错、冲突未裁决。定位看检索 query、候选集、分数、过滤条件、注入清单。

修复不同：写入污染靠准入、来源校验、去重、版本化、撤销；检索污染靠过滤、重排、时效、租户隔离、冲突裁决。没有写入证据和检索轨迹，两者分不开。

收束：错误写入看“来源/置信/重复/冲突/被纠正”信号；写入污染是“库里就错”，检索污染是“库对但召回/注入错”。定位靠写入证据链 vs 检索候选/注入轨迹，修复手段不同。

## 题3：同一条事实既在向量库又在结构化表，两边不一致时以谁为准？同步机制漏了会在哪个时序读到旧值？

以“权威源 + 版本/时间戳”为准，通常结构化表是事实权威，向量库是派生索引/检索副本；但按事实类型定：业务事实以业务库为准，偏好以结构化偏好表为准，向量库可重建。

不一致处理：

- 权威源优先：高风险/强一致事实以结构化表为准；向量库不一致时回填/重建，不反向覆盖权威源。
- 版本/时间裁决：比较 version、updated_at、来源；旧版本不生效。
- 读路径校验：读时校验版本/新鲜度，不一致告警/降级；高风险操作强制读权威源。

同步漏掉的时序：

- 权威源已更新、向量库未更新 → 检索召回旧值；异步队列延迟/失败/丢事件。
- 向量库先更新、权威源回滚 → 读到“新索引旧事实”。
- 缓存/TTL/多副本延迟；跨租户/多实例同步不一致。
- 写入成功但索引失败，或索引成功但事务回滚。

工程要求：权威源写 + outbox/事件 → 异步更新向量库；带版本/时效；对账/重建；读路径可校验；不一致告警。 向量库不是事实源，不能让它决定真相。

收束：结构化权威源定事实，向量库是派生索引；不一致以权威源+版本为准，向量库可重建。漏同步会在“权威已更新、索引未更新”或“索引先更新、权威回滚”的窗口读到旧值；要靠 outbox、版本校验、对账和重建兜底。

## 题4：“语义相似”被当成“当前相关”召回，是排序问题还是写入时就错了？怎么设计评测把两者拆开？

两者都可能，而且经常叠加。 写入时块切分/摘要/标签错、缺少作用域/时效/来源元数据、把不相关混入，排序再强也救不回；排序时只按向量相似、没有重排/过滤/任务上下文，就会把“像”当“该用”。

拆分方法：

- 固定写入集，只改排序：加过滤、重排、时效、任务上下文，看误召回是否下降 → 排序问题。
- 固定排序，清洗/重建写入集：修正块切分、标签、来源、时效、作用域，看是否改善 → 写入/索引问题。
- 负例集：构造“语义相似但不相关”的样本，测误召回率；正例集：构造“相关但不相似”的样本，测召回率。
- 指标分层：召回率（相关有没有进候选）、排序准确率（相关是否排前）、误召回率（相似不相关被注入）、端到端任务成功率；再按写入质量（块完整性、来源、标签）和排序质量（重排、过滤）分层。
- A/B：只改排序 vs 只改写入/索引，对比误召回和端到端。

收束：相似≠相关可能是写入错（元数据/块/来源缺失）或排序错（只看向量）；评测要固定一端改另一端，用“相似不相关负例 + 相关不相似正例”拆开召回、排序和端到端，不能只看总成功率。

## 题5：用户上周说 A、这周说 B，版本化保留后检索命中旧版本——失效标记应该写在写入侧还是检索侧？

两层都要，但权威状态写在写入侧，检索侧强制执行过滤；只写一侧会漏。

- 写入侧：新版本写入时标记旧版本 superseded/expired，记录 valid_from、valid_until、version、来源、时间；旧版本保留审计但不生效。写入侧是状态权威。
