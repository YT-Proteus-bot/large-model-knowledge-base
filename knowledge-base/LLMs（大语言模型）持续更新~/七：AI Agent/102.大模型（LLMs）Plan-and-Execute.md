# 102.大模型（LLMs）Plan-and-Execute

> 主题：LLMs（大语言模型）持续更新~ › 七：AI Agent　｜　原始文件：LLMs（大语言模型）持续更新~/七：AI Agent/102.大模型（LLMs）Plan-and-Execute.md

## 题1：什么是 Plan-and-Execute 范式？它与 ReAct 的根本区别是什么？

Plan-and-Execute 是一种将复杂任务的规划和执行显式分离的 Agent 架构范式。它首先由一个“规划器”对任务目标进行全局分解，生成一份结构化的、包含一系列有序子任务或步骤的“行动计划”，然后将这份计划交给一个“执行器”去逐步执行。这种范式的核心理念是“谋定而后动”，强调在动手之前先构建全局蓝图，以保证最终产出的结构完整性和逻辑一致性。

它与 ReAct 的根本区别在于对“规划”和“执行”的时空关系的处理。

ReAct 将规划和执行高度融合，形成一个实时的、步进的“思考-行动-观察”闭环。它不在行动前制定完整计划，而是每走一步都根据最新的环境反馈来决定下一步怎么走。这赋予它极大的灵活性和动态应变能力，但也使其容易在长程任务中迷失方向，缺乏对全局的掌控。

Plan-and-Execute 则将规划和执行严格分离，先完成规划，再按部就班执行。这种分离带来了几个关键优势：第一，它对最终产出有更强的全局控制和结构保证，特别适合格式严格、步骤明确的复杂任务；第二，它允许在执行前对计划进行审核和修正，高风险场景下可由人类把关；第三，执行过程相对简单、可预测，降低了在每一步都进行复杂推理的成本。其劣势在于对动态变化的适应能力较弱，当环境变化导致初始计划失效时，需要额外的重规划机制来补救。

简单类比，ReAct 像一位经验丰富的即兴爵士乐手，在舞台上根据现场氛围和同伴的演奏实时创造旋律，灵活但不确定；而 Plan-and-Execute 像一位建筑工程师，在施工前必须先完成详细的设计蓝图，然后严格按照图纸建造，确保最终的大楼稳固且符合预期。

## 题2：Plan-and-Execute 的典型流程：先由 Planner 生成完整计划，再由 Executor 逐步执行。

一个完整的 Plan-and-Execute Agent 工作流程，可以清晰地划分为两个宏观阶段和若干个关键环节，形成一个从“战略制定”到“战术执行”的完整闭环。

阶段一：规划

1. 接收任务与上下文：系统接收到用户的原始复杂目标，以及相关的背景信息（如用户画像、环境状态、可用工具列表等）。
1. Planner 生成计划：一个专门的、被提示为“战略规划师”的 LLM 被调用。它的输入是原始任务和上下文，输出是一份结构化、有序的、可执行的“行动计划”。这份计划将复杂目标分解为一系列逻辑依赖的子任务。计划中的每一步通常包含：步骤编号、子目标描述、需要执行的动作类型、动作所需的参数、以及该步骤所依赖的前置步骤。
1. 计划审核与确认：这是一个可选的、但极为重要的步骤。系统将生成的计划呈现给用户或一个独立的审核模块。用户可以在此阶段对计划进行审查、修改或确认。这能有效避免因规划错误导致后续大量无效的执行，尤其在高风险操作中不可或缺。

阶段二：执行

1. Executor 逐步执行：Executor 按顺序读取计划中的每一步。对于每一步，它根据子目标描述和动作类型，执行相应的操作。这可能是调用一个工具（如搜索、计算、代码执行）、生成一段文本，或者向用户发起一个澄清式提问。
1. 局部推理与状态更新：Executor 在执行每一步时，并非完全机械。它通常需要进行小范围的局部推理，例如，将上一步工具返回的结果填入下一步动作的参数中。Executor 还会维护一个“任务状态”，记录已完成的步骤、关键中间结果和当前进度。
1. 观察与评估：每一步执行完毕后，Executor 会评估该步的结果。它需要判断该步是否成功，结果是否满足该子目标的完成标准。
1. 异常处理与重规划触发：如果某一步执行失败，或者结果与预期存在重大偏差，Executor 会将该异常连同当前的任务状态，反馈给 Planner。Planner 被再次调用，基于最新的信息进行“增量重规划”或“全局重规划”，生成一个新版本的计划，替换或追加到原有计划中。然后执行器从更新后的断点继续执行。
1. 任务完成与交付：当计划中所有步骤都已成功完成，或者满足终止条件时，Executor 执行一个最终的整合步骤，将所有子任务的成果组装成用户所需的最终产出。

这个流程通过将“规划”和“执行”解耦，使得系统在结构性和灵活性之间找到了一个优秀的平衡点。

## 题3：如何设计 Planner 的提示模板，让它输出一个结构化、可执行的计划？

Planner 是整个 Plan-and-Execute 系统的战略大脑。其提示模板的设计，直接决定了生成计划的质量和可执行性。设计目标是引导模型进行严谨、全面、结构化的思考，而不仅仅是罗列一串动作。

核心设计要素

1. 角色设定与目标明确化：必须首先为模型设定一个高度具体的战略规划专家角色，并清晰地定义它的使命。例如，“你是一位资深的项目规划师，你的任务是为给定的用户目标，制定一份详尽、可执行的行动计划。”
1. 注入任务分解的元原则：在提示中明确指导模型如何进行高质量的分解。例如：“请遵循以下原则进行任务分解：① 自顶向下，先识别核心里程碑，再细化具体动作；② 每个子任务必须是一个原子操作，可以被一个工具调用或一个生成动作完成；③ 明确标注子任务之间的逻辑依赖关系；④ 确保所有子任务加在一起，能够完整地实现总目标，不遗漏关键步骤。”
1. 强制要求结构化的输出格式：这是实现自动执行的关键。必须要求模型以固定的、可被程序解析的格式输出计划。最常用的是 JSON，因为它可以清晰表达层级和属性。要求输出的 JSON 数组中，每个对象包含 step_id、goal、action_type、parameters、depends_on、expected_outcome 等字段。这为后续的 Executor 提供了明确的执行指令。
1. 提供高质量、多样化的少样本示例：抽象的指令不如鲜活的例子有效。在提示中提供 1-2 个完整的、从高维目标到详细计划的示例，展示如何正确处理依赖关系、如何将模糊意图转化为具体的工具调用，以及如何覆盖边界情况和失败的应对策略。示例是最好的老师。
1. 注入对可用工具的理解：Planner 在制定计划时，必须清楚地知道 Agent 有哪些工具可用。因此，提示中需要包含所有可用工具的详细描述（名称、功能、参数 Schema）。这使规划不会天马行空，而是建立在可实现的基础之上。

示例提示词片段

```
[系统] 你是一个世界级的任务规划师。你的职责是将一个复杂的用户目标，拆解成一个有序的、可执行的JSON计划。
[任务分解原则]
1. 自顶向下：先识别核心里程碑，再逐步细化每个里程碑下的具体动作。
2. 最小动作：每个子任务应该是一个原子操作。
3. 明确依赖：清晰地指出哪些任务是其他任务的前置条件。
4. 完整覆盖：确保所有子任务完成后，总目标可以被完美达成。
[可用工具]
- search(query): 搜索互联网信息。
- calculator(expression): 计算数学表达式。
[输出格式]
请严格以JSON列表格式输出你的计划，每个元素包含以下字段：
- "step": 步骤编号 (整数)
- "goal": 本步骤要达成的子目标 (字符串)
- "action": 需要执行的具体动作 (字符串)
- "depends_on": 依赖的步骤编号列表 (列表)
[示例]
...
[现在请处理]
总目标：{用户输入}
计划：
```
