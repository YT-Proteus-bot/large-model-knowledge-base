# 105.大模型（LLMs）Agent 框架（LangChain Agent、AutoGen）

> 主题：LLMs（大语言模型）持续更新~ › 七：AI Agent　｜　原始文件：LLMs（大语言模型）持续更新~/七：AI Agent/105.大模型（LLMs）Agent 框架（LangChain Agent、AutoGen）.md

## 题1：LangChain 的 Agent 抽象是如何设计的？AgentExecutor 的作用是什么？

LangChain 的 Agent 设计哲学是将大语言模型的推理能力与外部工具执行解耦，并通过一个统一的执行环境将它们编排在一起。这种抽象的核心是“Agent（智能体）”和“AgentExecutor（执行器）”的分离。

Agent 抽象

在 LangChain 中，Agent 并不是一个具体的类，而是一个逻辑概念，它的核心职责是决策。Agent 负责接收输入和历史上下文，然后输出一个结构化的“行动指令”。这个行动指令包含两个关键信息：要调用哪个工具，以及用什么参数。Agent 本身不执行任何操作，它只负责“想”和“决策”。LangChain 支持多种类型的 Agent，如 OpenAI Functions Agent、ReAct Agent 等，它们的主要区别在于如何构造提示、解析输出以及进行决策，但它们都遵循同一套抽象接口。

AgentExecutor 的作用

AgentExecutor 是 LangChain Agent 架构中真正的运行引擎，它负责实现“思考-行动-观察”的循环。AgentExecutor 将 Agent（决策大脑）和 Tools（执行手脚）连接起来，形成一个闭环。它的核心职责包括：

1. 循环控制：它运行一个死循环，不断地调用 Agent 进行决策。当 Agent 返回一个表示“任务完成”的最终答案时，执行器终止循环并将结果返回给用户。
1. 工具执行与观察注入：当 Agent 决定调用某个工具时，AgentExecutor 负责解析出工具名和参数，实际执行该工具，并捕获其返回结果。然后，它将这个结果格式化为一个“观察”文本，注入回对话上下文，供 Agent 进行下一轮思考。
1. 安全与边界控制：AgentExecutor 负责强制执行最大步数限制、处理工具调用超时和错误。这些边界控制是防止 Agent 陷入无限循环或产生错误的关键。
1. 提示词构造与上下文管理：它负责将系统提示、对话历史、工具描述和用户输入组装成完整的 Prompt，发送给 LLM。

通过这种 Agent 与 AgentExecutor 的分离，LangChain 实现了决策与执行的解耦，开发者可以灵活地替换不同的决策策略（Agent 类型），而无需改变执行层的逻辑。

## 题2：LangChain 中的 Agent 类型有哪些？OpenAI Functions Agent、ReAct Agent、Structured Chat Agent 的区别和适用场景。

LangChain 提供了多种 Agent 类型，以适应不同模型的能力和任务需求。它们的核心区别在于：如何构造提示、如何解析模型输出、以及如何利用模型特定能力。

1. OpenAI Functions Agent

这是专为 OpenAI 的 Function Calling 能力设计的 Agent。它不依赖传统的“Thought/Action”文本解析，而是利用模型原生支持的 tools 参数和 tool_calls 响应格式。

- 工作机制：提示中包含了工具的定义（JSON Schema）。模型直接输出一个结构化的 tool_calls 对象，包含函数名和参数。AgentExecutor 解析这个对象，执行工具，并将结果以 role: "tool" 的消息返回。
- 优点：极其可靠、无歧义，因为模型被专门训练来输出这种格式。支持并行工具调用。
- 适用场景：在使用 OpenAI 最新模型（GPT-3.5-turbo-0613 及更高版本）时，这是首选方案。适用于所有需要工具调用的通用场景。
1. ReAct Agent

这是最经典、最通用的 Agent 类型。它通过提示工程，引导模型生成“Thought（思考）”、“Action（行动）”、“Observation（观察）”的文本序列。

- 工作机制：提示词中包含一个详细的模板，告诉模型如何以这种交替格式输出。AgentExecutor 解析文本，提取出最新的 Action 指令，执行工具，然后将结果作为 Observation 追加回对话历史。
- 优点：模型无关，可以在任何支持指令遵循的 LLM 上使用，包括开源模型。其 Thought 过程完全透明，便于调试。
- 缺点：依赖于文本解析，格式错误可能导致执行失败。不支持原生并行调用。
- 适用场景：使用非 OpenAI 模型、需要高度可解释性的推理过程、或需要精细控制思考步骤的复杂多步任务。
1. Structured Chat Agent

这是一种支持多参数工具的高级 Agent，它将工具的参数 Schema 编码到提示中，允许模型在一次调用中为工具提供复杂的、结构化的输入。

- 工作机制：它的提示词包含了工具的参数 Schema 描述。模型可以生成包含结构化动作的文本，如 Action: Search 然后换行后跟 Action Input: {"query": "...", "source": "web"}。
- 优点：能够处理需要复杂参数的工具，比简单的单参数 ReAct Agent 能力更强。
- 适用场景：当你有多个工具，且它们的输入参数结构复杂（例如，需要嵌套对象或数组）时，这个 Agent 比基础的 ReAct Agent 更胜任。

## 题3：在 LangChain 中，如何定义一个 Tool？需要实现哪些接口？

在 LangChain 中，工具（Tool）是 Agent 与外部世界交互的唯一接口。一个设计良好的工具，能让 LLM 准确理解其功能和使用方式。

核心接口与定义方式

定义 Tool 最经典的方式是继承 BaseTool 类，并实现其核心方法。同时，LangChain 也提供了 @tool 装饰器，用最简洁的方式将普通函数封装为 Tool。

无论哪种方式，一个 Tool 的定义都包含以下几个关键部分：

1. name (str)

工具的唯一标识符。LLM 在决策时，会用这个名称来指定要调用的工具。名称应简洁、描述性强，最好使用动词-名词结构，如 search_documents、calculator。

2. description (str)

这是最重要的字段。它是 LLM 理解该工具功能、适用场景和参数含义的唯一依据。一个好的描述必须包含：

- 功能说明：工具做什么。
- 使用场景：什么时候应该用这个工具，而不是其他工具。
- 参数描述：清晰的语义和格式要求。
- 能力边界：这个工具不能做什么。
3. args_schema (Pydantic BaseModel)

定义工具输入参数的结构化 Schema。使用 Pydantic 模型来精确描述每个参数的类型、是否必需、以及描述信息。这使得 LLM 能够生成符合格式的参数，并且 LangChain 可以自动校验。

4. _run 或 _arun 方法

工具的核心执行逻辑。_run 是同步执行方法，接收参数，执行实际操作，并返回一个字符串结果。这个返回的字符串就是 LLM 下一次思考时看到的“观察”。

示例代码片段

```
from langchain.tools import BaseTool
from pydantic import BaseModel, Field
class SearchInput(BaseModel):
    query: str = Field(description="搜索关键词")
class CustomSearchTool(BaseTool):
    name: str = "search_web"
    description: str = "用于搜索互联网信息。当需要最新资料或时事时使用。"
    args_schema: type[BaseModel] = SearchInput
    def _run(self, query: str) -> str:
        # 这里是实际的搜索逻辑
        result = call_search_api(query)
        return result
```
